# Репозиторий Infragram

**Здесь лежат два несвязанных продукта.** Прежде чем что-то читать или менять,
посмотрите, что из этого живое.

## Что деплоится

Корневой `Dockerfile` + `railway.json` собирают и запускают ровно две вещи:

| Что | Где | Роль |
|---|---|---|
| **Infragram** | `tg-manager/` | Продукт: Telegram-инфраструктура и массовые операции. Бот на aiogram, HTTP-API мини-аппа, 53 фоновых цикла, исполнитель очереди операций |
| Личный ассистент | `assistant/` | Спутник: отдельный бот в том же контейнере, свой venv, на `tg-manager` не влияет (`start-all.sh`) |

Всё остальное в корне репозитория в контейнер **не попадает**.

## Что заморожено

Решение и обоснование: [`docs/adr/0001-one-kernel.md`](docs/adr/0001-one-kernel.md).

| Дерево | Состояние |
|---|---|
| `platform/` | Заморожен. Вторая, недоделанная реализация того же продукта на NestJS + Next.js: не исполняет операции, нет MTProto. Ценность — экраны дашборда, их предстоит перевести на `mini_app_api`. Новое сюда не добавлять |
| `nodes-service/` | Заморожен. Третья реализация, TS + gramjs. Предметная область переносится в `tg-manager` как тип операции |

## Что здесь вообще от другого продукта

Корневые `main.py`, `orchestrator.py`, `agents/`, `tools/`, `src/`, `supabase/`,
`basicfood-fixes/`, `database/`, `tests/` — это **BASIC.FOOD**, ИИ-агенты
интернет-магазина зоотоваров. Отдельный продукт, который живёт в этом
репозитории по историческим причинам и должен из него выехать.

Практическое следствие: корневой `main.py` представляется как «Pablo —
BASIC.FOOD AI agent system», хотя контейнер запускает `tg-manager/main.py`. Не
перепутайте — это разные файлы и разные продукты.

```bash
cd tg-manager
cp .env.example .env          # заполнить credentials
pip install -r requirements.txt
python -m pytest tests/ -q    # 3894 теста, ~2 минуты
python main.py
```

## Роли процесса

Один образ умеет подниматься тремя способами — `INFRAGRAM_ROLE`:

| Роль | Что делает | Когда нужна |
|---|---|---|
| `all` (по умолчанию) | Бот, HTTP и все фоновые циклы в одном процессе | Обычный деплой |
| `web` | Только бот и HTTP, без фоновых циклов | Когда мини-апп упирается в GIL, занятый операциями |
| `worker` | Только фоновые циклы, апдейты не забирает | Пара к `web` |

Важно: лимиты флуда живут в памяти процесса, поэтому **исполнителей операций
должен быть ровно один**. `services/replica_guard.py` бьёт хартбит и
предупреждает, если реплик оказалось больше: вторая молча разгонит темп по флоту
и это кончится банами. Разносить на `web` + `worker` безопасно — операции
остаются в одном процессе; поднимать два `worker` или два `all` — нет.
