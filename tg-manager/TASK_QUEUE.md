## OPEN

### 🔴 ОБЯЗАТЕЛЬНО В ПЕРВУЮ ОЧЕРЕДЬ — Infragram Virtual Layer (решение владельца)

Направление владельца: Infragram — не набор модулей, а вычислительный слой
поверх Telegram. «Telegram показывает, что произошло; Infragram строит модель
того, что происходит». Событие → интерпретация → состояние → решение → действие.

**Ядро СДЕЛАНО** (`services/virtual_layer.py`, схема v211, тесты
`test_virtual_layer_*`): динамическое СОСТОЯНИЕ (value + confidence + source +
распад + история) на любом уровне (user/bot/campaign/network); СИГНАЛ двигает по
лестнице воронки; распад остужает без подтверждения; КАСКАД (много «горячих»
детей → «горячий» родитель); на реальных переходах рождаются ВИРТУАЛЬНЫЕ
СОБЫТИЯ (purchase_intent_detected, user_lost_interest) в общую шину. Первый
источник сигналов подключён — сенсор намерений. Надстройка над
`unified_contacts.stage`, не второй источник правды.

**Осталось по слою (по убыванию отдачи):**
- [x] **Ещё источники сигналов** — 2026-09-25. `auto_responder` подаёт четыре:
      тап по инлайн-кнопке (`clicked_offer`), `/start` (`opened`), обычное
      сообщение (`replied`), стоп-слово и отписка (`unsubscribed`). Ключ —
      контакт владельца, резолвер по Telegram-id живёт в самом слое. Входящие
      из Хранилища и слушателя аккаунтов подают `replied` ДО разбора правил:
      раньше сигнал уходил только при смене стадии, и живая переписка без
      слов-триггеров оставляла слой в неведении, а распад остужал активного
      клиента. Осталось не подключённым: реакции на сообщения и
      вступления/выходы из каналов.
- [x] **Каскад bot←user в проде** — 2026-09-25. Связь «человек → бот» даёт
      `source` состояния ("bot_<id>"); `recompute_bot_cascade` считается в том
      же редком проходе организма, пороги ниже общих (5 при доле 10%), иначе
      для отдельного бота каскад недостижим. Температура ботов — в сводке слоя
      и на экране. **Каскад campaign←bot не сделан**: связи «бот → кампания»
      в слое пока нет.
- [x] **Автоматизации на виртуальных событиях** — 2026-09-25. Снимок мира несёт
      события за сутки (`became_ready_24h`, `cooled_24h`, `hot_bot`), мозг
      строит на них три подсказки; свежие решения вытесняют подсказку по
      накопленному списку.
- [x] **Экран состояний** — 2026-09-25. `entity_history` + временной рисунок
      (идёт вверх / заходил и уходил / остывает), маршрут
      `/api/miniapp/vlayer/entity/{type}/{id}`, переход внутрь с горячих строк
      и со строк ботов.

**Полезные механики из разбора владельца — в backlog этого направления:**
- [ ] **Intent Router**: «пиши что угодно» → определить намерение → направить к
      нужному боту/каналу (не в конкретный сценарий). 50 ботов → единый вход.
- [ ] **Automation Discovery**: находить повторяющийся ручной труд (менеджер шлёт
      одному клиенту один и тот же текст) → предлагать автоматизацию.
- [ ] **Invisible Trigger**: пользовательские триггеры, которых нет как событий
      Telegram («трижды посмотрел, не ответил») — строятся из виртуальных
      состояний этого слоя.
- [ ] **Mirror Bot / Clone Factory**: цифровой двойник бота для теста изменений
      на копии до реального трафика; массовое клонирование managed-ботов.

**Bot Mesh (боты координируют задачи) — ЯДРО СДЕЛАНО.** Telegram РЕАЛЬНО
поддерживает bot-to-bot (проверено по core.telegram.org/api/bots/bot-to-bot):
opt-in в @BotFather; в группах доставка по `/cmd@bot` или reply, в ЛС —
обоюдный opt-in, в бизнес-аккаунтах — только у отправителя. Гашение петель
Telegram НЕ делает — это на нас. Построено `services/bot_mesh.py` (схема v212):
конверт задачи + четыре независимых предохранителя (глубина, дедлайн, дедуп
шага через UNIQUE-индекс, цикл в трассе); любой в одиночку рвёт лавину.
Осталось:
- [ ] **Транспорт (отправка)**: приём подключён (auto_responder ловит
      bot-message, гасит петли, ведёт состояние). Физическая пересылка bot→bot
      изолирована в сиве и НЕ выверена на живых ботах — обкатать канарейкой на
      2 ботах после включения режима.
- [x] **Массовое включение opt-in** — bot_b2b + операция enable_bot_to_bot,
      группировка по аккаунту-владельцу, канарейка из UI (v213).
- [ ] **Маршруты из шаблонов**: связать с `network_builder` — топология сети
      задаёт маршрут задачи (Sales→Qualification→CRM).
- [ ] **Экран Mesh**: список задач, трасса передач, брошенные с причиной.
