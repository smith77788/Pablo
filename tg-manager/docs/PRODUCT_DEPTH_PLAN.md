# PRODUCT_DEPTH_PLAN.md — доводка продукта до «готового», а не MVP

**Статус: активный приоритет проекта.** Читать всем агентам перед работой над фичами.
Живой документ: punch-list ниже пополняется по мере аудита; сделанное — вычёркивать
(отметкой ✅ и коммитом), новое найденное — дописывать.

## Зачем это (диагноз)

Месяц несколько агентов наращивали ШИРИНУ (новые модули, плитки, экраны), но никто
не владел ГЛУБИНОЙ — «может ли живой пользователь пройти один ключевой путь от начала
до конца, ни разу не упершись в тупик или в тихий сбой». Итог: 98 плиток каталога,
400+ роутов — и при этом «Активен, но не работает», «Очищено 30», но не удалено,
сломанная кнопка «Создать», мёртвая «Карта связей», дубли-модули. Ощущение «сыро/MVP»
идёт НЕ от нехватки фич, а от того, что основным сценариям нельзя доверять.

## Метод (обязательный)

1. **Заморозка ширины.** Никаких новых модулей/плиток/экранов, пока живые не доведены.
   Исключение — только если новое прямо закрывает дыру в ключевом сценарии.
2. **Идти по пользовательским путям, не по фичам.** Берём ОДИН путь и доводим его до
   безупречного end-to-end: каждая кнопка работает, каждая нужная настройка на месте,
   каждое состояние даёт честную обратную связь, ноль тупиков и ноль «тихих успехов».
3. **Объективное «готово»** (см. `AGENT_PROTOCOL.md` → «Определение готово»): цепочка
   UI→route→handler→БД реально работает; нет мёртвых кнопок; действие даёт видимый
   результат; регресс-тест падает без фикса.
4. **Аудит перед доводкой.** Прежде чем чинить путь — пройти его насквозь и составить
   punch-list (файл/экран, что сломано/тупик/каких настроек не хватает, приоритет).

## Карта путей (порядок доводки)

1. **ЯДРО: аккаунт → операция** ← начинаем отсюда.
   Подключить аккаунт → прокси/IP-изоляция → прогрев → собрать аудиторию → запустить
   массовую операцию → увидеть реальный результат и здоровье аккаунтов.
2. **Контент → публикация.** Шаблоны/spintax → массовая публикация/быстрый пост →
   расписание → результат.
3. **Боты → аудитория → рассылка.** Создать/подключить бота → подписчики → воронки →
   рассылка → аналитика.
4. **Каналы.** Создание/управление → массовые действия → SEO/позиции.
5. **Наблюдаемость и настройки.** Дашборд как честное зеркало состояния + полнота
   настроек (глобальные, по-модульные, лимиты, прокси/IPv6, уведомления, тариф).

## Подозрения на недоработку (гипотезы — проверять по ходу, не факты)

Кросс-срезовые «сырые» сигналы, которые надо проверять на КАЖДОМ экране пути:
- **Пустые состояния.** Экран без данных объясняет, что делать дальше, или пугает
  пустотой/крутилкой? («нету информации» из скринов.)
- **Честная обратная связь.** После действия видно РЕАЛЬНЫЙ итог (успех/ошибка/почему),
  а не «поставлено в очередь» и тишина. Запрет «рапорт без эффекта».
- **Полнота настроек.** У модуля есть то, что реально нужно оператору (лимиты,
  расписание, фильтры, поведение), а не только «запустить». Это и есть «не хватает
  нужных настроек».
- **Нет тупиков.** С каждого экрана есть следующий логичный шаг; ошибки ведут к фиксу
  (релог, прокси, лимит), а не в никуда.
- **Загрузка/ошибки.** Есть внятные loading/error-состояния, не белый экран.
- **Консистентность.** Одинаковые названия/иконки для одного и того же; без дублей.
- **Мобильная вёрстка.** Это Telegram mini-app — узкий экран; без горизонтального
  скролла и схлопнутых кнопок.
- **Онбординг.** Новый пользователь понимает, с чего начать (первый аккаунт, первый
  прокси, первая операция).

Конкретные подозрения по ядру (проверить в аудите):
- Добавление аккаунта: понятно ли, КАК (бот/импорт сессии), и виден ли результат?
- Назначение прокси/IP-изоляции на аккаунт: доходит ли до эффекта, видит ли юзер?
- Прогрев: настройки достаточны? виден прогресс?
- Сборка аудитории → передача в операцию: связаны ли шаги, или это острова?
- Массовая операция: выбор целей, dry-run/канарейка, расписание, лимиты, живой
  прогресс, результат по каждой цели, ретрай упавших.
- Здоровье аккаунтов после операции: видно ли, что операция сделала с аккаунтами.

## ЯДРО «аккаунт → операция» пройдено (шаги 1–5)
Подключить аккаунт (в мини-аппе, с прокси) → прокси/IP виден и назначается →
аудитория из парсера сразу в рассылку/инвайт по запуску → массовая публикация с
канарейкой+подтверждением → влияние операции на аккаунты видно.
