# Audit Ledger — что уже реально проверено

Растущий журнал ревью, не вижн-документ. Цель: не проверять с нуля то, что уже
проверялось недавно, и не терять найденное между сессиями (см. `CLAUDE.md` —
раздел "Нет работающего механизма отслеживания охвата ревью").

Перед тем как аудировать область кода — проверь, нет ли свежей записи ниже.
Если есть и открытых находок не осталось — не аудируй с нуля, доверяй, но
пересматривай, если менялся сам код. После любого ревью — допиши запись сюда,
даже если ничего не нашли (это тоже сигнал: "проверено, чисто").

Формат записи:

```
## <модуль/файлы> — <дата>
Проверено: <что именно смотрели>
Найдено: <баги/риски или "ничего существенного">
Исправлено: <да/нет, коммиты>
```

## МОДУЛЬ Ecosystem Brain — Auto-Management: автодобавление каналов (Tier-1 4B) — 2026-07-12
Проверено: auto-* функции автоуправления (`auto_add_channels`, `auto_remove_dead_channels`, `auto_post_scheduling`, `balance_content`, `discover_channel_relationships`) — все 0 call-sites. Ключевая проверка: в ТУ ли таблицу они пишут, что читает система.
Найдено: **фиктивная фича** — `auto_add_channels`/`auto_remove_dead_channels`/`auto_post_scheduling` работают с `ecosystem_channels` (8 использований, все внутри этих же мёртвых функций), а РЕАЛЬНОЕ членство — `ecosystem_members` (60 использований; `get_members`+весь UI читают её; канонический источник каналов — `managed_channels.channel_id`, добавление через `add_member(object_type='channel')`). Подключение как есть = запись в мёртвую параллельную таблицу → каналы не появились бы в экосистеме (ровно ловушка CLAUDE.md #1/#3). Плюс `managed_channels` не имеет сигнала активности (только added_at) → надёжного «мёртвого» детектора для auto-remove нет.
Исправлено: частично (безопасный корректный кусок). `auto_add_channels` переписан на канонический путь (managed_channels → add_member → ecosystem_members, owner-scoped, идемпотентно, фильтр «недавно заведённые» = план 4B «автодобавление новых каналов»). Добавлены `set_auto_manage`/`is_auto_manage_enabled` (opt-in флаг в `ecosystems.meta.auto_manage` — БЕЗ миграции схемы) и фоновый цикл `run_auto_management` (раз в 6ч, только для opt-in экосистем, по умолчанию ВЫКЛ → нулевое изменение поведения). Цикл запущен в `main.py`. Тумблер в боте (`bot/handlers/ecosystems.py`, карточка экосистемы — «🤖 Автоуправление: ВКЛ/ВЫКЛ»). Регресс `tests/test_ecosystem_automanage.py` (6): каноничные таблицы, owner-scope тумблера, чтение флага, проводка в main. Осталось (бэклог): auto-remove (нужен надёжный dead-сигнал — активность канала), auto-post (создаёт операции — отдельное решение по объёму), уведомление владельца при автодобавлении (notify_if_enabled требует валидного pref), тумблер в mini-app UI.

## МОДУЛЬ Strike — anti-detection: guard повторного удара (Tier-1 3A) — 2026-07-12
Проверено: рандомизация интервалов и «не бить в одно время дважды» (план 3A) против реального strike-пути (`op_worker._exec_strike` → `strike_engine.staggered_strike`). Сверены 0-call-site хелперы: `get_randomized_interval`, `rotate_proxy_for_strike`, `is_strike_allowed`.
Найдено: (1) рандомизация интервалов уже есть де-факто — strike-путь насыщен `random.uniform` (staggers, wave cooldowns, inter-send), `get_randomized_interval` дублирует → не подключал. (2) `rotate_proxy_for_strike` — ОПАСЕН: `SELECT proxy_url FROM user_proxies WHERE is_active ORDER BY RANDOM()` без фильтра owner_id → сломал бы прокси-изоляцию (CLAUDE.md) и утёк бы cross-owner; НЕ подключать (латентный footgun, но dead → безвреден пока не вызван). (3) `is_strike_allowed` — готовый guard «не бить цель в интервал <4ч» (параллельная сессия уже починила его SQL-баг target_id→target), но dead code: в запуске strike НЕТ проверки повторного удара → детекшн-паттерн + износ аккаунтов. Матч чистый: `_exec_strike` кладёт сырой `target` в `StrikePlan(targets=[target])` → `r.target` == `strike_history.target` == аргумент `is_strike_allowed`.
Исправлено: да (по #3). Guard подключён в `_exec_strike` после валидации target: `min_restrike_hours` (default 4, настраивается), обход `params.force=True`; при недавнем ударе — status=done, ok=0, skipped=True + понятный summary (не failed — это осознанный пропуск, и не невалидный статус в очереди). Регресс `tests/test_strike_restrike_guard.py` (4): disallow при недавней записи, allow без неё, матч по колонке target, проводка в _exec_strike. Осталось (бэклог): показывать «цель недавно атакована, повтор через Nч / force» уже на запуске (endpoint) для мгновенного фидбэка; safe-версия rotate_proxy_for_strike со скоупом owner_id + изоляция, если понадобится.

## МОДУЛЬ Flood-движок — затухание штрафа по времени (надёжность) — 2026-07-12
Проверено: жизненный цикл `risk_score`/`consecutive_floods` в `_AccountFloodState` — растут в `record_flood`, убывают в `record_success` (−1 floods, −0.05 risk). Сверено покрытие: `record_flood` вызывается в 15 местах, `record_success` — только для part op-типов (publish/join/leave/strike). Time-decay искал в flood_engine и фоновых циклах (main.py).
Найдено: комментарий `record_flood` (стр. ~274) обещает "increases with floods, decays over time", но кода time-decay НЕТ — штраф убывает ТОЛЬКО через явный `record_success`. Для op-типов, которые пишут флуд, но не пишут успех, аккаунт держал завышенный множитель задержки (`recommended_delay`) и повышенный risk в выборе — до рестарта процесса (in-memory). Жёсткий `cooldown_until` истекает сам, а мягкий штраф — нет. Плюс подтверждено: `pacing_engine.should_pause()` только отображается в админке (1 call site), жёстко НЕ гейтит — сознательно не подключал (гейт по count-окну в 20 самоблокируется: пауза останавливает операции → окно не обновляется → дедлок; градуальное замедление через множитель уже закрывает «замедление при лимитах»).
Исправлено: да (частично — по мягкому штрафу). `_decayed_flood_penalty(state)`: read-only затухание по времени с последнего флуда (risk — полураспад ~30мин, consecutive_floods — −1/15мин), применяется в `recommended_delay`. Состояние не мутируется, `cooldown_until` не трогается. Регресс `tests/test_flood_decay.py` (5, monotonic мокается). НЕ инертное (ложный след, проверено): слой `anomaly_detector.run_anomaly_loop` РЕАЛЬНО запущен (`main.py:676`, мой прежний скан считал call-sites только в services/+bot/ и пропустил main.py). Осталось (бэклог): применить то же затухание в `account_rank_score` (выбор аккаунта тоже видит устаревший risk); дописать `record_success` для op-типов, где его нет; безопасная (time-boxed) версия should_pause если понадобится жёсткий тормоз.

## МОДУЛЬ Operation Engine — Circuit Breaker: потеря операции при паузе (Tier-1 1B) — 2026-07-12
Проверено: реальная проводка circuit breaker в `_run_op_task` (op_worker) — гейтит ли выполнение и что происходит с операцией при открытой цепи.
Найдено: гейт работает (строка ~1126 пропускает операцию), НО поллер атомарно ставит `status='running'` ДО запуска задачи (candidates-CTE), а при открытой цепи задача просто снимала op из `_active_op_ids` и выходила — операция оставалась `running`. Кандидаты отбираются только среди `pending` → повторно не бралась; восстанавливал только stale-watchdog по таймауту **60 мин** (`_STALE_RUNNING_TIMEOUT_MIN`), тогда как cooldown цепи всего 30 мин (`_CIRCUIT_BREAKER_COOLDOWN=1800`). Итог: операция висела в `running` до часа И держала фантомный слот параллельности владельца (`owner_running.running_count`), блокируя его ДРУГИЕ операции. «Пауза» фактически подвешивала очередь владельца.
Исправлено: да. `_release_op_for_circuit(pool, op_id, cooldown_s)` возвращает операцию в `pending` с `started_at=NULL` и `scheduled_for = now()+cooldown+5с` — повтор ровно после cooldown (кандидаты уважают `scheduled_for`, busy-loop исключён), фантомный слот освобождается сразу. Вызывается в ветке circuit-open (best-effort, сбой записи не ломает поток). Регресс `tests/test_circuit_release.py` (2): возврат в pending+deferred, устойчивость к нулевому cooldown. Осталось (бэклог): аналогичная ветка `waiting_approval` (строка ~1120) тоже оставляет op 'running' — проверить отдельно, там своя семантика (ждёт аппрува).

## МОДУЛЬ Выбор аккаунтов — Account Rotation / балансировка (Tier-1 2C) — 2026-07-12
Проверено: реальный путь выбора аккаунта под операцию — `resource_selector.select_account/select_accounts` → `flood_engine.get_best_account`; учёт trust_score, cooldown, наименее используемого. Плюс инертный `select_account_rotated`/`_record_account_usage` (in-memory, 0 call sites).
Найдено: trust_score и cooldown-исключение работают. НО балансировка нагрузки была не замкнута: `get_best_account` уже сортировал кандидатов `last_used ASC`, однако (1) финальный выбор переранжировал топ-10 чисто по риску, ИГНОРИРУЯ last_used — при ≤10 аккаунтах один и тот же (наибольший trust/наименьший риск) брался снова и снова; (2) `last_used` на этом пути НИКОГДА не обновлялся (пишется только в bot-path `get_active_account_for_owner`, импорте, авторегистре) → сортировка `last_used ASC` не двигалась. Итог: неравномерный износ, «любимый» аккаунт под повышенным риском бана — прямое противоречие миссии «аккаунты не ломаются».
Исправлено: да. `flood_engine.get_best_account` — добавлен `last_used` в выборку, мягкий `_recency_penalty` (max 0.08, полураспад 30мин — сдвигает выбор только среди почти равных, не жертвуя trust/риском) в финальном ранжировании, и best-effort `UPDATE last_used=now()` при выборе (замыкает петлю ротации). Регресс `tests/test_account_rotation.py` (4): форма штрафа, предпочтение наименее использованного среди равных, пометка использования, доминирование trust над recency. Осталось (бэклог): DB-backed usage-счётчик для многоворкерной среды (сейчас ротация опирается на last_used, что корректно между воркерами; in-memory `select_account_rotated` остаётся мёртвым — кандидат на удаление).

## tg-manager: Rotating proxy (P1 #6, ВЫСОКИЙ риск) — ручная ротация IP без потери изоляции — 2026-07-10
Контекст: последний открытый пункт моей полосы, помеченный как высокорисковый (класс AUTH_KEY_DUPLICATED). Сделал БЕЗ правки резолвера изоляции.
Инвариант, который держал: 1 аккаунт ↔ 1 УНИКАЛЬНЫЙ прокси; никогда сессия не работает с двух IP одновременно.
Как обеспечена безопасность:
  - Меняем ТОЛЬКО `proxy_id` в БД. `account_manager._resolve_client_proxy` НЕ трогаем — он читает актуальный proxy_id на старте каждой операции. Смена proxy_id видна лишь СЛЕДУЮЩЕЙ операции; параллельных операций на одном аккаунте не бывает (claim в op_worker) → одновременная работа сессии с двух IP исключена → нет AUTH_KEY_DUPLICATED.
  - Durable busy-сигнал `tg_accounts.in_operation` (TRUE на claim, FALSE на release) → в apply транзакция + `SELECT … FOR UPDATE` блокирует строки, гвард `COALESCE(in_operation,FALSE)=FALSE` при UPDATE — занятые аккаунты не ротируются даже при гонке с claim (кросс-процессно).
  - Пул исключает прокси, занятые ЛЮБЫМ не-ротируемым аккаунтом (busy в группе или вне группы) → ротируемый не получит чужой прокси (изоляция с не-ротируемыми сохранена).
Планировщик (чистый, `services/proxy_rotation.py::plan_rotation`): инъективная перестановка (циклический сдвиг) → назначенные прокси попарно различны. Фикспоинт: при пуле меньше числа аккаунтов выкидывает из пула прокси «скипнутых» аккаунтов (иначе скипнутый удержал бы прокси, отданный ротируемому → коллизия). Доказано exhaustive-тестом (перебор n×k, инвариант «нет двух аккаунтов на одном прокси» + «нет дубля в плане»).
НАЙДЕН баг в ходе тестирования (мой же exhaustive-тест): наивный сдвиг давал коллизию со скипнутым аккаунтом при малом пуле → добавлен фикспоинт, тест закреплён.
UI: кнопка «🔁 Ротация IP» на экране Прокси + `rotateProxies()`. Проводка UI→route(/api/miniapp/proxy/rotate)→endpoint полная.
Верификация: +7 tests/test_proxy_rotation.py (перестановка+изоляция; краевой малый пул со скипом; больше аккаунтов чем прокси; NULL текущие; пустой пул/одиночные; exhaustive n×k; проводка транзакция+FOR UPDATE+гвард+route+UI). Полный tests/ зелёный (exit 0). Python AST + node JS чисто.

## tg-manager: горизонтальная обрезка слева (Аккаунты/шаблоны) — overflow-x на .screen — 2026-07-12

Причина по CSS: `.screen{position:absolute;inset:0;overflow-y:auto}` — БЕЗ overflow-x. По спеке CSS, если один axis overflow=auto, а другой visible, второй computes to `auto` → любой чрезмерно широкий потомок делает ВЕСЬ экран горизонтально прокручиваемым/панящимся → при смещении контент клиппится слева (ровно как на скринах). Стандартный remedy «страница скроллится по горизонтали».
