# AUDIT_LEDGER — память агента между сессиями

Журнал переписан с нуля под новый режим работы. Прежние ~1170 строк находок — в
git-истории (`git log -- docs/AUDIT_LEDGER.md`), не в этом файле. Ключевые
инварианты, которые прежде жили здесь (секреты зашифрованы, операции — только
через `operation_bus.submit`, техдолг index.html/schema), перенесены в
`../CLAUDE.md` → «Проектные факты».

## Зачем этот файл
Кодовая база большая — за один проход её не покрыть. Без учёта уже проверенного
каждая новая сессия либо повторяет чужую работу, либо верит документам на слово
вместо проверки кода. Этот журнал — растущая память покрытия ревью между
сессиями.

## Формат записи (новый режим: одна запись = один урок)
Первая строка — однострочное резюме. Далее — детали. Обновляй существующую запись,
а не дублируй; удаляй запись, оказавшуюся неверной.

```
## <модуль/файлы> — <дата> — <однострочное резюме урока>
Проверено: <что именно смотрели>
Найдено: <баг/риск или «ничего существенного»>
Исправлено: <да/нет; коммит; регресс-тест>
```

Перед объявлением области проверенной — смотри сюда: если она уже здесь с недавней
датой и без открытых находок, не проверяй с нуля. Нашёл баг → фикс + регресс-тест
(в том же коммите) + запись сюда.

**Как вести этот файл (память ≠ свалка):** хронология ниже растёт — но переиспользуемое
знание живёт в СВОДЕ ниже (держи его компактным, это «индекс» памяти). Разрастётся
>~900 строк → дистиллируй новые уроки в свод и подрежь хронологию (прежнее остаётся в
`git log`). НЕ храни здесь: код/пути/структуру (читать из репо), git-историю, дубли
`CLAUDE.md`/`PRODUCT_DEPTH_PLAN.md`, временное состояние задач. Высшая ценность —
исправления обратной связи пользователя и классы багов (свип-листы), а не пересказ фич.

## СВОД: классы багов (свип-лист — проверяй каждый на новом экране/исполнителе)

1. **Admin cross-tenant ↔ owner-scoped.** Счётчик/список/фильтр по `owner_id` там, где
   экран для админа межтенантный → «0 при N на экране» или «0 строк → падение
   операции». Скоуп счётчика обязан совпадать со скоупом экрана. (dashboard `_stats`/
   acc_health; «Проверить все»/`_exec_check_accounts_health`.)
2. **Второй источник правды.** UI пишет в один стор, движок читает другой → «тихий
   успех» (тумблеры уведомлений: settings_json vs notification_settings). Здоровье
   аккаунта — только `get_account_health`, не второй счётчик.
3. **Параметр принят, но не доходит до эффекта/не персистится.** (`record_flood`
   ронял `operation_id`; превью получателей игнорировало сегмент.)
4. **Fake/silent success.** Тост «готово» без проверки реального итога; счётчик = вход,
   а не факт. Итог операции обязан нести причину провала до экрана.
5. **Мёртвая кнопка.** `onclick`→несуществующая JS-fn ИЛИ `api()`→несуществующий роут.
   Гейты: `test_no_dead_onclick_handlers`, `test_no_dead_api_routes` (сканируют
   index.html + `mini_app/screens/*.js`).
6. **Дубль-определение** (хендлер/роут/JS-fn) затеняет рабочий. Гейт:
   `test_no_duplicate_definitions` — доверяй ему как страховке.
7. **Anti-detection: парные требования на КАЖДОМ аккаунт-текст-сендере** — spintax-на-
   цель + `is_account_quarantined` ПЕРЕД действием + честный показ пропуска. Общий
   помощник `_filter_quarantined_accounts` (fail-open). Свип: `grep account_manager.
   (send_dm|post_to_channel)` — до конца по всем совпадениям, а не по первым.
8. **Счётчик done>total.** Пере-подхват op с тем же id (retry / watchdog / старт
   воркера) без сброса `done_items`. Сбрасывать при requeue И при старте исполнителя.
9. **Пауза без возобновления.** Любая `paused`-сущность обязана иметь resume ТАМ ЖЕ,
   где список/пауза; перед включением resume — проверить идемпотентность движка (не
   перешлёт ли повторно).
10. **Таймзона.** datetime-local → `toISOString()` (UTC) → `fromisoformat` (tz-aware) →
    показ обратно в локальном.
11. **Сырой 500 наружу.** Бэкенд отдаёт `_err(str(exc),500)` → пользователь видит
    нечитаемый/утечный текст. Санитайзить на клиенте (generic для 500), деталь — в
    логах. 12. **Застрявшая крутилка = тупик.** Загрузчик ставит spin-wrap, а catch
    только тостит → крутилка навсегда, повтора нет. catch обязан вернуть кнопку/
    контент (гейт test_no_stuck_spinner). 13. **Некликабельный ряд-тупик.** Ряд
    списка (`cursor:default`, без `onclick`) для сущности, у которой ЕСТЬ детальный
    или управляющий экран → тап в никуда. Если тот же список в другом месте
    кликабелен (воронки: `funList` немой vs `bfList` → `openFunnelDetail`), это
    палево несогласованности. Ряд обязан вести в деталь/менеджер. Исключение:
    чисто информационные логи/сводки (история, «последние N», парсенные юзеры) —
    там `cursor:default` легитимен. 14. **Fire-and-forget задача без ссылки = GC-риск.**
    `asyncio.create_task(...)`/`get_event_loop().create_task(...)` без сохранённой
    ссылки: event loop держит на задачу лишь СЛАБУЮ ссылку → GC может собрать её до
    завершения (тихая смерть фонового цикла/операции). Долгоживущие циклы и критичные
    задачи обязаны держать ссылку (модульная переменная / set + `add_done_callback(
    set.discard)` / await напрямую / task_registry). Свип: `grep -n 'create_task('` —
    для каждого проверить, удержана ли ссылка. Гейт: test_no_unreferenced_bg_tasks.
15. **Строка вместо datetime в TIMESTAMPTZ = фича мертва.** asyncpg на `str` для
    timestamptz кидает ошибку → хендлер падает ВСЕГДА (фича есть в UI, но не
    работала никогда). Так умерли CRM-напоминание, schedule_post, отложенные
    рассылки и mass_publish по расписанию.
    **ВАЖНАЯ ПОПРАВКА (2026-07-29, найдено прогоном по живой БД):** прежняя
    редакция этого пункта утверждала, что «спасает явный `$N::timestamptz`». Это
    НЕВЕРНО и само по себе уводило в сторону. asyncpg выводит тип параметра ИЗ
    ЗАПРОСА: увидев `$5::timestamptz`, он ТРЕБУЕТ datetime и падает на строке ещё
    до похода в Postgres. Каст не парсит — он только объявляет тип. Так молча
    ломался `operation_bus.submit(scheduled_for=...)`, у которого каст был.
    **Спасает ТОЛЬКО разбор в `datetime` на границе** (наивное время → UTC, иначе
    класс 10). Свип: найти timestamptz-колонки → проверить, что во ВСЕХ вызовах
    туда идёт datetime, а не строка; наличие `::timestamptz` доказательством не
    считать. Прямой INSERT в operation_queue — двойной запах: и обход шины, и
    отсутствие единой точки разбора.
    Метод: на заглушке пула этого не видно вообще — фейковый `fetchrow` принимает
    что угодно. Тип параметра проверяет только живой драйвер.
16. **Тихое протухание от времени (без единой ошибки).** Отпечатки клиента, версии
    зависимостей, «актуальные» списки — стареющие активы: код не меняется, а
    правдоподобие падает само. Для anti-detection это КОГОРТНАЯ СИГНАТУРА (все
    аккаунты одинаково устарели → похожи друг на друга, не похожи на живых).
    Асимметрия: версия ПРИЛОЖЕНИЯ стареть не должна (автообновляется у всех),
    модель УСТРОЙСТВА — должна (телефон держат 3-4 года); пул из одних новинок так
    же палевен, как из одного старья. Лечится НЕ разовым бампом (протухнет снова),
    а механизмом: env-переопределение без деплоя + дата ревизии + гейт по возрасту.
    Гейт: test_fingerprint_freshness.
17. **Предварительная нарезка работы = тихая потеря задач.** Массовый исполнитель
    режет цели по исполнителям ЗАРАНЕЕ (`_chunks`/срез по индексу), и кусок намертво
    принадлежит своему аккаунту. Любой ранний выход из его цикла (`break` по флуду,
    `continue` по исчерпанному лимиту, исключение движка) уносит ВЕСЬ остаток куска
    в никуда — без ошибки, без записи, без строчки в итоге. Рядом при этом простаивают
    аккаунты, уже закончившие свои куски. Лечится общей ОЧЕРЕДЬЮ: аккаунты разбирают
    её по батчу за круг, неотработанный хвост возвращается в голову, выбывает аккаунт,
    а не его доля аудитории. Парные требования к такому циклу: (а) считать прогресс
    по ФАКТИЧЕСКИ обработанным (`ok+failed`), а не по размеру оборванного батча;
    (б) отличать сбой ЦЕЛИ (закрытая группа) от сбоя аккаунта — иначе очередь заставит
    весь флот разбиваться об одну и ту же цель кругами; (в) выводить аккаунт из круга
    при нулевой отработке, иначе цикл вечный; (г) показывать остаток очереди в итоге —
    молчаливый недобор это тихий провал (класс 4). Свип: `grep -n '_chunks\|// n_accs\|
    \[i::'` по исполнителям. Гейт: test_invite_queue_scheduler.
18. **«Данных нет» часто значит «их не сохраняли».** Признак, которого якобы нет в
    системе, нередко ПРОХОДИТ через код и выбрасывается: `me` из Telethon даёт
    Premium/аватар на каждой проверке здоровья, `parsed_audiences.source_username`
    даёт источник каждой цели. Симптом-близнец — отдельная функция, делающая СВОЙ
    коннект ради признака, который уже был в руках десятью строками выше (лишний
    след на аккаунте, класс #16). Свип: для каждого «неучитываемого» признака
    искать не колонку в схеме, а вызов, через который он проходит. Парное правило:
    **NULL ≠ False** — нужна отметка времени проверки, иначе «не спрашивали»
    неотличимо от «нет», и объект штрафуется за пробел в НАШИХ данных.
19. **Anti-detection: ритм ≠ след, и порядок — тоже подпись.** Адаптивные паузы
    делают человечным ТЕМП, но состав вызовов остаётся машинным: аккаунт, у
    которого в API только `InviteToChannel` × N, отделяется от живого тривиально.
    Отдельно: любая выгрузка `ORDER BY` отдаёт данные сгруппированными, и массовая
    операция, идущая по этому порядку, воспроизводит группировку источника в своём
    трафике. Свип по сендерам: не только «есть ли задержка», но и «из чего состоит
    поток вызовов» и «в каком порядке идут цели».
20. **Совместимая сигнатура ≠ совместимая семантика.** Когда параллельная ветка
    расширяет ОБЩУЮ функцию новым параметром с дефолтом, старые вызовы продолжают
    компилироваться и проходить тесты, но получают ДРУГОЕ поведение (так
    `render_pattern(rng=None)` сделал предпросмотр недетерминированным: имена в
    превью и при создании расходились). Свип при любом rebase, затронувшем общий
    рендер/форматтер: `git diff <база>..HEAD -- <общий модуль>` → для каждого
    нового параметра с дефолтом найти ВСЕ существующие вызовы и решить, верен ли
    для них дефолт. Второй след того же класса — перегрузка одного символа двумя
    механизмами (`|` = и разделитель пула, и spintax): добавляя разделитель,
    проверить, не занят ли он соседней фичей.
21. **Построено ≠ подключено.** Готовый, покрытый тестами сервис без строки
    запуска неотличим от отсутствующего, а схема с триггером, пишущим в таблицу,
    которую никто не читает, — это растущий мусор вместо фичи (`immunity_engine`:
    312 строк, тесты, триггер в проде, ноль обработанных событий). Симметрично на
    фронте: событие, которое бэкенд считает и шлёт по SSE, без подписчика просто
    выбрасывается (`op_complete`). Свип: (а) список `_resilient("…")` в `main.py`
    против сервисов с `async def run/start`; (б) `await push("X"` в API против
    `addEventListener('X'` во фронте; (в) таблицы из свежих схем — есть ли
    SELECT хоть где-то.
22. **Отказ по правилу — не сбой сервера.** Исключение бизнес-правила (тариф,
    лимит, квота), пойманное общим `except Exception` и отданное как 500, делает
    ПЛАТНУЮ функцию похожей на СЛОМАННУЮ: пользователь идёт в поддержку с багом
    вместо кассы. Свип: для каждого исключения-правила найти ВСЕ вызовы поднимающей
    функции и проверить, что перед общим `except Exception` стоит свой перехват;
    плюс страховка на уровне приложения (middleware) для тех, кого добавят потом.
    Гейт-храповик обязателен: один новый хендлер молча возвращает всё назад.
23. **Заглушка пула не проверяет типы параметров.** Фейковый `fetchrow(q, *a)`
    принимает что угодно, поэтому ошибки СВЯЗЫВАНИЯ (str вместо datetime, dict
    вместо jsonb, int вместо bigint[]) на юнит-тестах невидимы в принципе —
    зелёный прогон тут ничего не доказывает. Так пережил релиз сломанный
    `submit(scheduled_for=...)`, убивавший ВСЕ отложенные операции продукта.
    Правило: для цепочек, где ошибка стоит пользователю сценария (очередь
    операций, планировщик, массовые действия), хотя бы раз прогнать путь по
    настоящему postgres со всей схемой — поднимается за пару минут и ловит то,
    чего не увидит ни один мок. Симметрично для фронта: реальный рендер вместо
    проверки строк в HTML.
24. **Ненаходимая функция = отсутствующая функция.** Пользователь жалуется «не
    хватает функций/настроек» чаще не потому, что их нет, а потому что: (а) поиск
    не читает описания/синонимы, которые УЖЕ есть в коде; (б) инструмент общего
    назначения зарыт в детали частного объекта (глобальный поиск — во вкладке
    одного бота); (в) живой бэкенд-флаг (колонка в notification_settings, поле в
    submit) не имеет контрола в UI. Свип при жалобе на навигацию/нехватку: поиск
    каталога должен матчить label+desc+keywords; каждый top-level инструмент
    достижим с верхнего уровня; каждый читаемый движком флаг настройки — с
    тумблером. Гейты: test_catalog_search_semantic, test_settings_notification_prefs.


**Правила проверки:** «Проверено» = проследить цепочку до ЭФФЕКТА (runner шедулится в
`main.py`? параметр доходит до БД?) + одна edge-проверка, а не «эндпоинт существует».
Фронт-аудит ВСЕГДА включает `mini_app/screens/*.js`. Проверяй по РЕАЛЬНОМУ пути, не
только юнит-тестом.

## Класс #1: админ ВСЕГДА видел все аккаунты платформы (два админ-профиля = одинаковые 25) — 2026-07-30 — межтенантный срез был по умолчанию, а не по опт-ину
Контекст: пользователь — «в обоих админ-профилях вижу одинаковых 25 подключённых
аккаунтов». Ожидание: каждый профиль видит СВОИ.
Проверено: все места, где `admin = _is_admin(uid)` меняло скоуп списка аккаунтов в
`services/mini_app_api.py`: `accounts` (список), `account_detail`, `accounts_export`,
`accounts_check` («проверить все»), `accounts_mass` (масс-операции + select_all_filtered),
дашборд `_stats`/acc_health, SSE-поток `events`. Бот-сторона (`db.get_tg_accounts`) и
`dashboard_visual` — уже owner-scoped, там чисто.
Найдено: любой админ ВСЕГДА получал межтенантный срез (`WHERE TRUE`, без owner) — без
единого явного запроса от фронта (фронт вообще не шлёт scope-параметр). Значит админ
не мог увидеть свои аккаунты, а «проверить все»/масс-операции шли по ЧУЖИМ. Два
админ-профиля → идентичный список всей платформы.
Исправлено: да — платформенный срез стал ЯВНЫМ опт-ином: `?scope=platform` (query) или
`{"scope":"platform"}` (тело) и только у админа; по умолчанию всё owner-scoped даже у
админа. Хелперы `_wants_platform_scope`/`_body_wants_platform_scope`. Коммит + регресс
`tests/test_accounts_owner_scoped_by_default.py` (падает без фикса).
Урок: «админ = видит всё» не должно быть ДЕФОЛТОМ для owner-данных — межтенантный доступ
это явный опт-ин, иначе тихий cross-tenant и на чтении, и на записи. Скоуп счётчика
дашборда обязан следовать за скоупом экрана (класс #1) — оба привязаны к одному опт-ину.

## tg-manager: горизонтальная обрезка слева (Аккаунты/шаблоны) — overflow-x на .screen — 2026-07-12

Причина по CSS: `.screen{position:absolute;inset:0;overflow-y:auto}` — БЕЗ overflow-x. По спеке CSS, если один axis overflow=auto, а другой visible, второй computes to `auto` → любой чрезмерно широкий потомок делает ВЕСЬ экран горизонтально прокручиваемым/панящимся → при смещении контент клиппится слева (ровно как на скринах). Фикс: добавлен `overflow-x:hidden` на `.screen`. Внутренние намеренные горизонтальные скролл-ряды (`.acc-kpi` и т.п.) имеют СВОЙ `overflow-x:auto` и продолжают скроллиться независимо — фикс их не ломает. Стандартный remedy «страница скроллится по горизонтали». Требует подтверждения на устройстве (в песочнице нет рендера Telegram-мини-аппа), но изменение низкорисковое (в худшем случае — без эффекта, вёрстку не ломает).
