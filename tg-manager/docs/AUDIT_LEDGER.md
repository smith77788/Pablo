
## tg-manager: политика прокси — выбор strict/allow_direct + low_risk-операции без прокси — 2026-07-07
Запрос: (1) функции без массовых быстрых действий не должны гарантированно требовать прокси; (2) система должна давать выбор — работать только через прокси или разрешить без прокси (с риском блокировок). Плюс это вероятная причина, почему контакты не синхронизировались.
Найдено: `_resolve_client_proxy` жёстко поднимал `ProxyIsolationError`, если аккаунту назначен прокси, но URL пустой/битый — БЕЗ различия рисковости операции и без пользовательского выбора. Одиночное чтение (контакты) блокировалось так же, как массовое действие.
Сделано:
  - Чистый модуль `services/proxy_policy.py`: `proxy_decision(has_proxy_url, proxy_parsed_ok, policy, enforce, low_risk) → use|block|fallback`. Инварианты: валидный прокси → use; low_risk НИКОГДА не block (fallback на прямое/TG_PROXY); битый НАЗНАЧЕННЫЙ прокси при не-low_risk → block (не уводим прокси-аккаунт в сеть напрямую втихую — изоляция); нет прокси + strict/enforce → block, иначе fallback.
  - `_resolve_client_proxy(device, low_risk)` и `_make_client(session, device, low_risk=False)` — новый флаг (обратносовместим для всех 91 вызова). Глобальная политика: env `PROXY_POLICY` (default allow_direct) + per-owner override `device['proxy_policy']`.
  - Owner-политика: `db.get_proxy_policy(pool, owner)` читает `platform_users.settings_json.proxy_policy`; `get_account_for_telethon` докладывает `proxy_policy` в словарь аккаунта (теперь возвращает dict, +owner_id в SELECT). Эндпоинт settings уже сохраняет весь JSON.
  - `get_contacts` помечен `low_risk=True` → чтение контактов больше НЕ требует прокси: при allow_direct аккаунт с мёртвым/отсутствующим прокси уходит на прямое соединение и контакты синхронизируются (вероятный корень жалобы). Прямое соединение логируется (риск бана).
  - UI: в «Настройки → Безопасность» селектор «Политика прокси» (Только через прокси / Можно без прокси), грузится с бэка, сохраняется в settings_json.
Верификация: 1203 теста (+8 test_proxy_policy: все ветки решения, low_risk-инвариант, strict/allow_direct, enforce, normalize, проводка low_risk в get_contacts и proxy_policy в get_account_for_telethon; починен стаб _resolve_client_proxy в test_session_encryption под новую сигнатуру). Python AST + node JS чисто.
Осталось: прокинуть per-owner proxy_policy в массовый путь (resource_selector строит словари аккаунтов иначе — сейчас там действует процессная PROXY_POLICY/enforce, не per-owner); пометить остальные одиночные читающие операции low_risk (login_code/check_restriction идут через profile_setter_engine._connect — отдельный проход).

## tg-manager: политика прокси — проводка в массовый путь + low_risk для одиночных чтений — 2026-07-07
Добивка backlog предыдущей записи (выбор strict/allow_direct теперь действует и на массовых операциях; остальные одиночные чтения не требуют прокси).

Одиночные account-picks через flood_engine (select_account) owner_id в словарь не кладут → там действует процессный дефолт, не per-owner (одиночные, низкий риск; отдельный проход при необходимости).
Верификация: 1206 тестов (+3 к test_proxy_policy: проводка per-owner в массовый путь — кэш/owner_id в селекторе/прайм в op_worker; honor _low_risk + пометка инлайн-чтений). Python AST + node JS чисто.

## tg-manager: КРИТИЧНО — low_risk-прямое соединение убивало сессии (AUTH_KEY_DUPLICATED) — 2026-07-07
Регрессия МОЯ (введена в прошлой прокси-правке). Симптом (скрин пользователя): контакты не синхронизируются, в деталях по аккаунтам — «The authorization key (session file) was used under two different IP addresses simultaneously, and can no longer be used (AUTH_KEY_DUPLICATED)».
Причина: `proxy_decision` при `low_risk` уходил на `fallback` (прямое соединение) ДАЖЕ если аккаунту назначен прокси, но его URL битый/неактивен. Сессия привязана к IP прокси; коннект контактов-синка с СЕРВЕРНОГО IP (или конкурентно с другим IP) → Telegram НЕОБРАТИМО инвалидирует сессию. Т.е. «чинил» синхронизацию контактов ценой убийства сессий — худший класс бага по CLAUDE.md (потеря изоляции/аккаунтов).
Исправлено: порядок в `proxy_decision` изменён — битый НАЗНАЧЕННЫЙ прокси теперь → `block` ВСЕГДА (в т.ч. low_risk и allow_direct): нельзя подключать прокси-сессию с другого IP. `fallback`(прямое) остаётся только для аккаунтов БЕЗ назначенного прокси (их каноничный транспорт — прямое, сменой IP не рискуем). Тесты обновлены: `test_broken_assigned_proxy_blocks_ALWAYS_even_low_risk`. Плюс sync_account ловит AUTH_KEY_DUPLICATED → метит аккаунт acc_status='session_expired' + понятная причина «нужна переавторизация» (уже убитые сессии Telegram не вернуть — их надо перелогинить).
Верификация: мои затронутые тесты зелёные (proxy_policy 11, contacts 14, geo/stage/pagination). 2 падения в наборе — внешние (contacts_hub/trust_engine, commit 3c4c4092 другого агента), не мои.
Вывод пользователю: чтобы работать БЕЗ прокси — снять назначение прокси с аккаунтов (тогда прямое безопасно); при назначенном прокси сессию нельзя дёргать с другого IP. Уже показавшие AUTH_KEY_DUPLICATED сессии — перелогинить.

## tg-manager: прокси v2 — резолвер по proxy_id + масс-снятие прокси («обе возможности») — 2026-07-07
Продолжение критического фикса. Пользователь: контакты/действия ДО СИХ ПОР не идут без прокси (скрин снова AUTH_KEY_DUPLICATED). Дыра в моём первом фиксе: `_resolve_client_proxy` опирался на `proxy_url` (результат JOIN `is_active=TRUE`). У аккаунта с НАЗНАЧЕННЫМ proxy_id, но НЕАКТИВНЫМ прокси, proxy_url=NULL → код считал его «без прокси» → уходил напрямую → снова убивал сессию.
Исправлено (безопасность): резолвер теперь «привязан к прокси» = `proxy_id задан ЛИБО есть url`. proxy_id-назначен + url нет (неактивен) → block (не подключаем прокси-сессию с чужого IP). Прямое соединение — только для аккаунтов БЕЗ proxy_id.
Добавлено (обе возможности эксплуатации):
  - Работать С прокси — назначение прокси аккаунту (было, `account_set_proxy`).
  - Работать БЕЗ прокси — снятие прокси: массовый op `detach_proxy` в accounts_mass (UPDATE proxy_id=NULL, owner-скоуп, работает и с select_all_filtered) + кнопка «🔌 Снять прокси» в баре массовых действий (единичное снятие уже было через account_set_proxy proxy_id=null). После снятия аккаунт не привязан к IP прокси и коннектится напрямую.
Важно (в комм. пользователю): аккаунты, УЖЕ показавшие AUTH_KEY_DUPLICATED — мертвы на стороне Telegram (перелогин). Снятие прокси на живом аккаунте безопасно, если далее он используется ТОЛЬКО напрямую (последовательная смена IP ок; фатальна лишь одновременная работа с двух IP).
Верификация: 13 tests/test_proxy_policy (+2: резолвер учитывает proxy_id; масс-detach owner-скоуп+NULL). Python AST + node JS чисто.

## tg-manager: перелогин убитых сессий — оказалось УЖЕ реализовано, доведена видимость — 2026-07-07
Запрос «массовый перелогин». Проверка показала: инфраструктура УЖЕ есть и полна — бот `cb_reauth_list` (action reauth_list) выводит список всех аккаунтов `acc_status='session_expired'` с кнопкой «🔄 Релог» на каждый; `cb_relog` (action relog, accounts.py:1405) шлёт SMS-код по сохранённому номеру → ввод кода → восстановление сессии. Мой фикс AUTH_KEY_DUPLICATED уже метит убитые сессии как session_expired → они автоматически попадают в этот список. Т.е. «массовый помощник перелогина» = существующий Переавторизатор, ничего строить не нужно.
Доведено: в mini-app аккаунты `session_expired` были неотличимы (показывались как «Выкл»). Добавлен отдельный статус в карточке («🔑 Релог») и в детали («Нужна переавторизация — в боте: Аккаунты → Переавторизатор»), чтобы пользователь видел, какие аккаунты требуют релога и куда идти. Проверено: обе callback-ветки (reauth_list, relog) существуют — не мёртвые кнопки.
