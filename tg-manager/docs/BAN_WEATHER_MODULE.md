# 🌩 Ban Weather — иммунная система флота

> Замыкает петлю **исход → причина → защита**: каждая смерть аккаунта становится
> сигналом, который автоматически бережёт остальной флот.
> На этот файл ссылаются docstring'и `services/immunity_engine.py` и
> `services/account_status.py`.

## Зачем

Аккаунты банятся **волнами**: Telegram меняет детект скачками. Инструменты на
рынке реагируют пост-фактум и держат anti-detection статическим конфигом.
Никто не превращает сам факт смерти в автоматическую защиту живых. Поймать
паттерн за 30–60 минут до того, как он выкосит флот, — это сохранить сотни
аккаунтов.

## Ниша среди существующих сервисов (что НЕ дублируем)

| Сервис | Что делает | Отношение к модулю |
|---|---|---|
| `trust_engine`, `account_health` | Считают ЗДОРОВЬЕ аккаунта (0.1–1.0) | Потребляем как признак |
| `account_monitor` | Ловит мёртвые сессии | Источник событий смерти |
| `account_rehab` | Апелляция спамблока, реабилитация | Работает ПОСЛЕ смерти |
| `op_worker`, `strike_engine` | Исполняют операции | Точка, которую гейтим |
| `infra_advisor`, `infra_copilot` | Рекомендации по состоянию | Не имеют обратной связи по исходам |

**Пустая ниша:** иммутабельный лог исходов, автопсия, обнаружение вспышек и
автоматический стоп-кран. Ни один сервис этого не делал.

## Фаза 1 — фундамент

- **`account_status_events`** — иммутабельный лог всех смен `acc_status`.
- **Триггер `trg_immunity_capture_status`** на `tg_accounts` ловит **любой** путь
  смены статуса (их ~13 в коде + будущие). Ключевое решение надёжности: захват
  не зависит от дисциплины вызова, горячие файлы править не нужно.
- **`services/account_status.py`** — централизованный мутатор для ОБОГАЩЕНИЯ
  события (reason/source/context). Уже используется `account_rehab`.
- **`immunity_engine`** — снапшот окна признаков за 72ч → **автопсия**
  (вероятная причина, сравнение с выжившими, предлагаемое правило) и
  **сигнатура смерти**.

**Сигнатура:** `op_mix × geo × warm_bucket × trust_bucket`, например
`mass_invite|geo=DE|warm=fresh|trust=low`. Детерминированная — по ней считаем
выживаемость и вешаем политики.
Важно: шкала `trust_score` в проекте **0.1–1.0**, пороги 0.3/0.7 (не 0–100).

## Фаза 2 — детектор вспышек

`detect_outbreaks()` наполняет `immunity_signatures`: `deaths_1h`, `deaths_24h`,
`exposures_24h` (живые аккаунты владельца), `death_rate`, `threat_level`.

**Вспышка = УСКОРЕНИЕ смертности** относительно собственной суточной нормы
(плюс доля выкошенного флота), а не абсолютное число — так волна ловится в
начале:

| Уровень | Условие |
|---|---|
| `storm` | ≥3 смертей за час при ускорении ≥3× **или** ≥50% флота за сутки |
| `warning` | ≥2 за час при ускорении ≥2× **или** ≥30% |
| `watch` | ≥2 смертей за сутки **или** ≥15% |
| `calm` | иначе (<2 смертей за сутки — статистический шум) |

**Затухание — по факту отсутствия смертей в 24-часовом окне, а не по времени
строки.** Версия «по `updated_at`» не срабатывала никогда: активные строки
обновляются каждым проходом, и «погода» показывала бы шторм сутки спустя.

## Фаза 3 — предохранитель

При `storm` взводится запись в `immunity_policy` и `operation_bus.submit`
поднимает `ImmunityBlockedError` (наследник `PermissionError` → middleware
мини-аппа отдаёт чистый 403 с текстом причины, а не 500).

Консервативно по умолчанию:
- блокируется **только конкретный `op_type`** этого владельца, не весь флот;
- **только на шторме** (`warning` — предупреждение оператору, не остановка);
- cooldown 30 мин, **снятие автоматическое** по `until`;
- **fail-open**: любая ошибка проверки НЕ мешает работе;
- kill-switch `IMMUNITY_BREAKER=0`.

## Модель данных

- `account_status_events(id, acc_id, owner_id, old_status, new_status, is_death,
  reason, source, context, autopsy, signature, processed_at, created_at)`
- `immunity_signatures(signature, owner_id, deaths_1h, deaths_24h,
  exposures_24h, death_rate, threat_level, updated_at)`
- `immunity_rules(id, owner_id, match, action, source, enabled, cooldown_sec, note)`
- `immunity_policy(id, owner_id, op_type, signature, action, reason, until, auto)`

Схема: `schema_v146_ban_weather.sql` (идемпотентная).

## Принципы

- **Триггер-first захват** — ни одна смерть не теряется.
- **Чистая логика отделена от БД** (`compute_signature`, `build_autopsy`,
  `classify_threat`, `op_type_from_signature`) — тестируется без PostgreSQL.
- **Объяснимость** — каждое авто-действие несёт человекочитаемую причину.
- **Fail-soft/fail-open** — иммунитет это страховка, а не критический путь.
- **Каждая фаза с регресс-тестами** и проверкой на реальном PostgreSQL.
