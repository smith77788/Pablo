# 🌩 Ban Weather — Иммунная система флота (Fleet Immune System)

> Предиктивная защита от банов, которая **учится на исходах**: превращает
> каждую смерть аккаунта в сигнал, автоматически защищающий остальных.
> Занимает пустую нишу поверх существующих сервисов — не дублирует их.

## Зачем (единственная экзистенциальная боль ботовода)

Аккаунты банятся **волнами** (Telegram меняет детект скачками). Все инструменты
на рынке реагируют пост-фактум и держат anti-detection как статический конфиг
(прокси+девайс один раз). Никто не замыкает петлю: **смерть → почему → авто-защита живых**.
Поймать паттерн за 30–60 минут до того, как он выкосит флот, — это спасти сотни аккаунтов.

## Позиционирование среди наших сервисов (что НЕ дублируем)

| Сервис | Что делает | Отношение к модулю |
|---|---|---|
| `trust_engine`, `behavioral_engine`, `account_health` | Проактивно **считают** скоры аккаунтов | Мы **потребляем** их скоры как признаки |
| `account_monitor` | Ловит мёртвые сессии → `session_expired` | Один из источников событий смерти |
| `strike_engine`, `invite_engine` | **Исполняют** операции | Точки, которые мы **гейтим** предохранителем |
| `infra_advisor`, `infra_copilot` | Рекомендации по состоянию | Мы даём **обратную связь по исходам**, которой у них нет |

**Пустая ниша, которую занимаем:** иммутабельный лог исходов, автопсия, обучение
на смертях, обнаружение вспышек, автоматический стоп-кран. Ни один сервис этого не делает.

## Архитектура (5 фаз)

### Фаза 1 — Фундамент: Status Event Ledger + Автопсия
- **`account_status_events`** — иммутабельный лог всех смен `acc_status` c флагом смерти,
  местом для автопсии/сигнатуры (заполняется движком асинхронно).
- **Триггер `trg_immunity_capture_status`** на `tg_accounts` — гарантированно ловит
  **любой** путь смены статуса (их ~13 в коде + будущие), не требуя правок горячих файлов.
  Это ключевое решение надёжности: захват не зависит от дисциплины вызова.
- **`services/account_status.py`** — централизованный мутатор `set_status(...)` для
  **обогащения** события (reason/source/context). Опционален для захвата, обязателен
  для качества данных; сайты мигрируют постепенно.
- **`services/immunity_engine.py`** — фоновая обработка: снапшот окна признаков за
  72ч (из `operation_log`/`operation_queue`/`infra_memory_accounts` + гео/сабнет прокси
  + возраст прогрева + trust/health на момент смерти), генерация **автопсии** (что делал,
  чем отличался от выживших, вероятная причина, предлагаемое правило) и **сигнатуры смерти**.

### Фаза 2 — Детектор вспышек (Ban Weather)
Скользящий анализ выживаемости по сигнатурам: `death_rate(signature, window)` против
базовой линии. Аномальный рост → «горящий паттерн» + уровень угрозы (`immunity_signatures`).
«Прогноз погоды банов» на уровне флота.

### Фаза 3 — Автоматический предохранитель (Circuit Breaker)
Два хука: `operation_bus.submit` (гейт `op_type` для владельца) и выбор аккаунта в
`op_worker` (отсев рисковых). Консультация `immunity_policy`: throttle / bench / quarantine
с cooldown, **объяснимой причиной** и авто-восстановлением, когда волна спала.

### Фаза 4 — API + вкладка «🌩 Ban Weather»
Эндпоинты (прогноз, горящие паттерны, лента автопсий, правила, что авто-приостановлено).
Вкладка в едином дашборде (`dashboard.js`).

### Фаза 5 — Cross-fleet (опт-ин)
Анонимизированные сигнатуры смертей агрегируются между операторами (по согласию) →
раннее платформенное обнаружение волн. **Ров/moat с сетевым эффектом**: одиночный скрипт
это воспроизвести не может (нет cross-fleet данных).

## Модель данных (Фаза 1)

- `account_status_events(id, acc_id, owner_id, old_status, new_status, is_death,
  reason, source, context jsonb, autopsy jsonb, signature, processed_at, created_at)`
- `immunity_signatures(signature, owner_id, deaths_1h, deaths_24h, exposures_24h,
  death_rate, threat_level, updated_at)` — кэш-роллап (наполняется в Фазе 2)
- `immunity_rules(id, owner_id, match jsonb, action, source, enabled, cooldown_sec, note, created_at)`
- `immunity_policy(id, owner_id, op_type, signature, action, reason, until, auto, created_at)`

## Сигнатура смерти

Канонический ключ для группировки исходов:
`op_mix × geo_country × proxy_subnet(/24) × warming_bucket × trust_bucket`.
Детерминированная строка → по ней считаем выживаемость и вешаем правила/предохранитель.

## Принципы

- **Триггер-first захват** — ни одна смерть не теряется, горячие файлы не трогаем.
- **Чистая логика отделена от БД** — `compute_signature`/`build_autopsy` тестируются без БД.
- **Объяснимость** — любое авто-действие предохранителя несёт человекочитаемую причину.
- **Fail-soft** — сбой движка/детектора не блокирует операции (только снимает защиту).
- **Каждая фаза — с регресс-тестами** (правило CLAUDE.md).
