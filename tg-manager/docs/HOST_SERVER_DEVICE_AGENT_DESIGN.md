# Host-Server: Device-Compute Agent — дизайн (для ревью, НЕ для прода)

> Статус: **ДИЗАЙН**. Ничего из исполнительного слоя не включено в прод.
> Гейт `services.host_server.device_compute_execution_enabled()` → `False`.
> Этот документ — предмет security-ревью ПЕРЕД любой реализацией агента.
> Модель данных, согласие, оплата и учёт аренды (`host_offerings`/`host_rentals`)
> уже работают; здесь проектируется только сценарий 3 — запуск инфраструктуры
> арендаторов на устройстве владельца за арендную плату.

## 1. Что мы вообще строим (и почему это опасно)

Владелец устройства (host) добровольно отдаёт свои вычислительные мощности.
Платформа устанавливает и запускает на его устройстве инфраструктуру **других**
пользователей (tenant) — Telegram-аккаунты/воркеры массовых операций — и платит
host'у аренду.

Это по сути **исполнение чужого кода/нагрузки на чужом физическом железе**.
Классы риска, которые обязаны быть закрыты ДО запуска:

1. **RCE-класс**: tenant не должен получить произвольное выполнение вне песочницы
   на устройстве host'а. Ошибка = взлом чужого компьютера.
2. **Кража секретов**: сессии/прокси tenant'а (зашифрованы `token_vault`) не
   должны утекать host'у; личные данные host'а не должны утекать tenant'у или
   платформе сверх необходимого.
3. **Юридическая ответственность host'а**: с его IP/устройства пойдут действия
   tenant'а. Требуется явное информированное согласие + отзыв + прозрачность, что
   именно исполняется, и жёсткие политики допустимого (никакого нелегального
   контента — переиспользовать существующие safety-гейты).
4. **Anti-detection слой** (ядро продукта): изоляция прокси-под-аккаунт и
   отсутствие палевных сигнатур обязаны сохраняться и в распределённом режиме —
   иначе бан tenant-аккаунтов дороже фичи.
5. **Доступность/доверие**: host может внезапно выключить устройство, отозвать
   согласие, оказаться вредоносным (подменять/снифать нагрузку).

## 2. Цели и НЕ-цели

**Цели**
- Безопасно исполнять изолированную нагрузку tenant'а на устройстве host'а.
- Явное, скоупленное, **отзываемое** согласие host'а; мгновенный teardown при отзыве.
- Честный учёт (метрики → `host_rentals`) и оплата за фактическое время/мощности.
- Сохранить изоляцию прокси/сессий и safety-гейты платформы.

**НЕ-цели (сознательно вне объёма первой версии)**
- Произвольный код tenant'а. Только **декларативные, предопределённые типы
  ворклоадов** платформы (например «крутить N Telethon-воркеров с такими лимитами»).
  Tenant НЕ загружает бинарники/скрипты.
- P2P между host и tenant напрямую. Всё через control plane платформы.
- Использование мощностей host'а под что-либо, кроме заявленного типа ворклоада.

## 3. Роли и компоненты

```
┌─────────────┐    mTLS/gRPC     ┌──────────────────┐
│  Control     │◀───────────────▶│   Device Agent    │   (на устройстве host'а)
│  Plane       │  assign/heartbeat│   (наш бинарь)     │
│ (платформа)  │  revoke/teardown │  ┌──────────────┐ │
│              │                  │  │ Sandbox (jail)│ │  ← изолированный ворклоад
│ host_nodes   │                  │  │  tenant work  │ │     tenant'а
│ node_workload│                  │  └──────────────┘ │
│ consent_log  │                  └──────────────────┘
└─────────────┘
      ▲ секреты выдаются кратко-живущими, scoped, через brokered-доступ
      │ (session_str/proxy НЕ лежат на диске host'а в открытом виде)
```

- **Control Plane** — существующая платформа: назначает ворклоады, хранит
  согласия, метрит, платит, отзывает. Единственный посредник host↔tenant.
- **Device Agent** — наш подписанный бинарь, который host осознанно ставит.
  Регистрирует ноду, держит heartbeat, принимает **только** декларативные задания,
  поднимает песочницу, репортит метрики, немедленно сносит по revoke.
- **Sandbox** — изоляция ворклоада (см. §6).

## 4. Модель данных (предлагается; НЕ применено)

```
host_nodes(
  id, owner_id (host), offering_id → host_offerings,
  node_pubkey,            -- ключ агента (регистрация/attestation)
  status,                 -- registered|online|offline|revoked|banned
  capabilities JSONB,     -- cpu/ram/os/net, задекларированные и измеренные
  last_heartbeat_at, created_at
)

node_workloads(
  id, node_id → host_nodes, rental_id → host_rentals, tenant_id,
  workload_type,          -- ЗАКРЫТЫЙ список ('tg_worker_pool', ...)
  spec JSONB,             -- лимиты: max_accounts, cpu%, ram_mb, net_kbps
  status,                 -- assigned|installing|running|stopping|stopped|failed
  started_at, stopped_at
)

consent_log(               -- неизменяемый журнал согласий/отзывов
  id, owner_id, offering_id, action,  -- granted|revoked
  scope JSONB,             -- на что именно согласился (тип, лимиты, safety-политика)
  ip, user_agent, created_at
)

node_metrics(              -- честный учёт для оплаты
  id, node_id, workload_id, ts, cpu_pct, ram_mb, net_bytes, uptime_s
)
```

Связь с готовым: `host_offerings.allow_device_compute` = верхнеуровневое согласие
на листинге; `consent_log` = точечное информированное согласие на КОНКРЕТНЫЙ
ворклоад/аренду. Оба необходимы; ни одного недостаточно без включённого гейта.

## 5. Жизненный цикл ворклоада

1. **Регистрация ноды**: host ставит агент → агент генерит keypair → регистрирует
   `host_nodes` (pubkey) → control plane привязывает к offering владельца.
   Attestation ноды (что это наш неизменённый агент) — см. открытые вопросы §9.
2. **Аренда**: tenant арендует offering (уже работает). Провайдер подтверждает →
   `host_rentals.status=active`.
3. **Информированное согласие**: перед первым назначением host видит ТОЧНО, что
   будет исполняться (тип, лимиты, safety-политика, что пойдёт с его IP) и жмёт
   «согласен» → запись в `consent_log(action=granted, scope=...)`.
4. **Назначение**: control plane создаёт `node_workloads(assigned)` и шлёт агенту
   декларативный spec (никакого кода). Секреты tenant'а (session_str/proxy) —
   **brokered**: не кладутся на диск host'а; см. §6.
5. **Установка/запуск**: агент поднимает песочницу по spec, стартует
   предопределённый ворклоад-тип с лимитами → `running`.
6. **Heartbeat + метрики**: агент шлёт живость и `node_metrics`. Нет heartbeat >
   порога → ворклоад считается упавшим, tenant переназначается, оплата host'у
   останавливается по факту.
7. **Отзыв согласия / съём offering / конец аренды**: control plane шлёт `revoke`
   → агент **немедленно** останавливает и уничтожает песочницу и все секреты в
   памяти → `stopped` + `consent_log(action=revoked)`. Отзыв всегда выигрывает.
8. **Оплата**: из `node_metrics`/uptime считается фактическая аренда → расчёт
   host'у (интеграция с существующей платёжной/комиссионной логикой).

## 6. Изоляция и секреты (сердце безопасности)

- **Песочница**: ворклоад tenant'а — в жёстком контейнере/микро-VM (gVisor/
  Firecracker-класс, либо OS-нативный jail), с:
  - сетью только к нужным Telegram/прокси-эндпоинтам (default-deny egress);
  - без доступа к ФС host'а, буферу обмена, другим процессам;
  - cgroups-лимиты CPU/RAM/IO/сети из `spec` (host не «выжигается»).
- **Прокси-изоляция сохраняется**: каждый tenant-аккаунт ходит через свой прокси
  (как в основном движке) — распределённость НЕ ломает per-account изоляцию.
- **Секреты не оседают у host'а**: `session_str`/`proxy_url` остаются
  зашифрованы (`token_vault`); в песочницу отдаются кратко-живущим, scoped
  brokered-доступом, только в память, стираются при teardown. Host не может их
  прочитать (иначе украдёт tenant-аккаунты).
- **Host защищён от tenant'а**: песочница не может выйти к данным/железу host'а
  за пределы выданной квоты.
- **Платформа не сверх-собирает**: с устройства host'а не тянем ничего, кроме
  метрик и телеметрии здоровья.

## 7. Safety / легальность

- Переиспользовать существующие safety-гейты (запрет нелегального контента):
  ворклоад-тип не должен позволять то, что запрещено платформой.
- Host в согласии видит категорию активности; может ограничить типы.
- Полный неизменяемый аудит (`consent_log` + `node_workloads` + метрики) —
  и host, и платформа видят, что исполнялось.

## 8. Поэтапный вывод (каждый этап — за гейтом, с ревью)

- **Э0 (сделано)**: данные/согласие/оплата/маркетплейс. Гейт off.
- **Э1**: агент + attestation ноды + heartbeat, БЕЗ исполнения (только регистрация
  и метрики железа). Внутренние устройства.
- **Э2**: изолированная песочница + ОДИН предопределённый ворклоад-тип, brokered
  секреты, revoke→teardown. Только доверенные host'ы (сотрудники), канарейка.
- **Э3**: ограниченный публичный бета с явным согласием, лимитами, аудитом.
- Гейт включается по-этапно, не раньше прохождения security-ревью этапа.

## 9. Открытые вопросы для ревью

1. **Attestation**: как убедиться, что на ноде наш неизменённый агент, а host не
   снифает ворклоад? (подпись бинаря, TPM/remote attestation — где возможно; где
   нет — считать host'а полу-доверенным и НЕ давать ему plaintext-секретов вообще).
2. **Юрисдикция/ответственность**: чей риск, когда с IP host'а идёт tenant-действие?
   Нужна юридическая формулировка согласия + гео-политики.
3. **Технология песочницы** под целевые ОС (host'ы — это десктопы/телефоны?).
   На мобильных полноценная изоляция может быть недостижима → возможно ограничить
   device_compute только десктоп-ОС.
4. **Anti-abuse**: вредоносный host, ворующий/ломающий tenant-нагрузку; вредоносный
   tenant, атакующий host'а через ворклоад. Репутация нод, канарейки, отзыв.
5. **Экономика**: тариф аренды device_compute, комиссия платформы, гарантии
   доступности (SLA host'а).

## 10. Что НЕ делаем до прохождения ревью

Не пишем и не включаем: приём произвольного кода, plaintext-секреты на диске
host'а, egress без allowlist, исполнение без `consent_log`-записи, обход
safety-гейтов, мобильные host'ы без доказанной изоляции. Гейт
`device_compute_execution_enabled()` остаётся `False`, пока Э2-ревью не пройдено.
