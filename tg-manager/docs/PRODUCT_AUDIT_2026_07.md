# Аудит продукта Infragram — 2026-07-26

Аудит проведён по коду, не по документам. Каждая находка воспроизводима
командой, приведённой в разделе «Как проверено». Цифры — на момент аудита.

Принцип отбора: улучшение должно **достраивать существующее**, а не добавлять
подсистему. Все семь находок укладываются в существующую архитектуру;
пять из семи — меньше 300 строк.

## A-1 (P0). Движок иммунитета флота написан, но никогда не запускается

**Почему это проблема.** `services/immunity_engine.py` (13 КБ, 13 функций) —
Ban Weather / Fleet Immune System: разбор смертей аккаунтов, сигнатура смерти,
автопсия, предлагаемые правила. Триггер БД `trg_immunity_capture_status`
(`schema_v146_ban_weather.sql`) **живой** — он пишет каждое изменение статуса
аккаунта в `account_status_events`. Обработчик `immunity_engine.start(pool)`
не вызывается нигде. Таблица копит события, которые никто не читает; таблицы
`immunity_signatures`, `immunity_rules`, `immunity_policy` остаются пустыми.

Anti-detection — заявленное конкурентное преимущество продукта. Здесь готовый
аналитический контур этого преимущества выключен одной ненаписанной строкой.

**Как пользователь сталкивается.** Никак — и в этом суть: аккаунты умирают,
причины не накапливаются, повторные баны по той же причине ничем не
предотвращаются. Пользователь видит только «аккаунт улетел» и не получает
ни разбора, ни правила на будущее.

**Минимальное изменение.** Одна строка в `main.py` рядом с остальными 39
циклами + проверка, что фаза 1 (обработка событий) не требует ничего сверх
существующих таблиц:

```python
asyncio.create_task(_resilient("immunity_engine", immunity_engine.start, pool))
```

**Переиспользуем.** `_resilient` (уже есть), `bg_tasks.spawn`, схема v146
целиком, `infra_memory` для чтения признаков.

**Файлы.** `main.py` (импорт + запуск), возможно
`services/immunity_engine.py` (сигнатура `start` уже `(pool, interval_sec)`).

**Регрессии.** Цикл ходит в БД каждые 120 с — нагрузка мала, но при большой
`account_status_events` первый проход разберёт всю историю. Ограничить первый
батч (`process_pending(limit=100)` уже ограничен). Fail-soft заявлен в
докстринге — проверить, что исключение внутри не роняет `_resilient`.

**Тесты.** `test_immunity_engine_wired.py`: (1) `immunity_engine` присутствует
в списке запускаемых циклов `main.py` — статический гейт, как
`test_no_unreferenced_bg_tasks`; (2) `process_pending` на пустой таблице
возвращает 0 и не бросает; (3) `compute_signature` детерминирована.

**Объём.** ~10 строк кода + ~40 строк тестов.

## A-2 (P0). «Повторить только упавшие» есть у 1 операции из 64

**Почему это проблема.** `operation_log(op_id, step_num, target, status,
message)` заполняется **в 45+ местах** `op_worker.py` — то есть per-target
результат есть почти у каждой массовой операции. Но кнопка «🔁 Повторить
неудавшиеся» выдаётся только для `mass_publish` (`op_worker.py:1633`),
и реализация (`bot/handlers/mass_publish.py:574`) знает конкретные поля
(`text`, `media_file_id`, `channel_ids`).

Для остальных 63 типов операций частичный провал означает: перезапускать всё
целиком. На массовой операции это дорого (лимиты аккаунтов) и опасно —
успешные цели обрабатываются повторно, что даёт дубли.

**Как пользователь сталкивается.** Операция на 400 каналов, 27 упали по
FloodWait. В уведомлении — «⚠️ 373 ок, 27 ошибок» и кнопка «Детали».
Дальше тупик: чтобы добить 27, надо вручную собрать их из деталей и завести
операцию заново.

**Минимальное изменение.** Декларативно описать в `OP_REGISTRY`, какое поле
`params` содержит список целей и что означает `operation_log.target`:

```python
"mass_invite": {..., "targets_param": "account_ids", "target_kind": "int"},
```

Затем одна универсальная функция и одна кнопка:

```python
async def retry_failed_targets(pool, owner_id, src_op_id) -> int | None:
    # failed = SELECT DISTINCT target FROM operation_log WHERE op_id=$1 AND status='error'
    # new_params = {**src_params, meta["targets_param"]: failed}
    # return await submit(pool, owner_id, op_type, new_params, total_items=len(failed))
```

Кнопка добавляется в существующий блок `op_worker.py:1625+` условием
«у op_type есть `targets_param` и `_failed > 0`» — вместо жёсткой проверки
`op_type == "mass_publish"`.

**Переиспользуем.** `operation_log` (уже пишется), `operation_bus.submit`
(идемпотентность и лимиты плана уже внутри), паттерн из
`mass_publish.cb_mpub_retry_failed` — обобщается почти дословно,
`BmCb`/`MassPubCb` для callback.

**Файлы.** `services/operation_bus.py` (+`targets_param` в метаданные
операций, у которых поле известно — начать с `account_ids`: 30 использований,
и `channel_ids`: 4), `services/op_worker.py` (условие кнопки),
`bot/handlers/mass_ops.py` (универсальный обработчик; существующий
`mass_publish` оставить — он умеет медиа).

**Регрессии.** Главная — повторить цель, которая на самом деле прошла:
`operation_log` пишется не единообразно (где-то `status='ok'`, где-то только
ошибки). Поэтому брать **только** `status='error'` и дедуплицировать. Вторая —
`target` в логе не всегда совпадает по типу с элементом `params` (строка против
int): нужен `target_kind` и явное приведение, иначе исполнитель получит пустой
список и «успешно» ничего не сделает. Третья — двойной retry одной операции:
ограничить кнопку одним нажатием (по факту создания дочерней операции).

**Тесты.** `test_universal_retry_failed.py`: (1) для op_type с `targets_param`
кнопка появляется, без него — нет; (2) в новые params попадают ровно упавшие
цели и ничего лишнего; (3) `status='ok'` не попадает в повтор; (4) нечисловой
`target` при `target_kind='int'` отбрасывается, а не роняет обработчик;
(5) при нуле упавших — честное «повторять нечего», а не пустая операция.

**Объём.** ~120 строк кода + ~90 строк тестов.

**Сделано 2026-07-26 — с существенной поправкой к оценке охвата.**
При реализации выяснилось, что `operation_log.target` у большинства
исполнителей — это **исполнитель** (`f"acc#{acc['id']}"` у всех `boost_*`,
`bulk_set_profile`, `mass_report`) или человекочитаемая метка (`title`,
`display_name`, `str(label)[:64]`), а не идентификатор цели. Повтор «по
упавшим» для них либо бессмыслен (повторять теми же аккаунтами, которые
только что упали по флуду), либо невозможен — метка необратима в id.

Поэтому механизм сделан **декларативным и узким**: работает только для
op_type, объявивших `retry_targets` в `OP_REGISTRY`. Сейчас это три операции
с проверенным обратимым форматом — `bulk_join` (target = сама ссылка),
`bulk_leave` (`str(channel)`), `bulk_seo_apply` (`ch#<id>`); `mass_publish`
сохранил собственный обработчик, умеющий переносить медиа. Добавление
следующей операции стоит одной строки в реестре — но только после сверки
формата её лога.

Исходная оценка «63 операции» была неверной: она следовала из факта «лог
пишется в 45 местах» без проверки, ЧТО именно туда пишется.

## A-3 (P1). 92 % пустых экранов мини-аппа не имеют кнопки действия

**Почему это проблема.** Функция `empty(ico, txt, sub, action)` в
`mini_app/index.html` **уже поддерживает** четвёртый аргумент — кнопку-CTA.
Из 206 вызовов её передают 15. Остальные 191 объясняют пользователю словами,
что надо сделать: «Нажмите + Создать», «Добавьте канал через меню в Telegram».

Пустой экран без действия — тупик первого запуска: именно на нём новый
пользователь решает, работает продукт или нет.

**Как пользователь сталкивается.** Открывает «Каналы» — «Нет каналов.
Добавьте канал через меню в Telegram». Куда именно идти, экран не говорит и
никуда не ведёт.

**Минимальное изменение.** Добавить четвёртый аргумент к самым посещаемым
пустым экранам. Это не новая функциональность — вызовы функций для перехода
уже существуют (`openChannels`, `openGpCreate`, `openAccounts`…).

**Переиспользуем.** `empty()` целиком, существующие функции навигации,
существующие модалки создания.

**Файлы.** `mini_app/index.html` (точечно), `mini_app/screens/*.js`.

**Регрессии.** `onclick` на несуществующую функцию = мёртвая кнопка; это
ловится существующим гейтом `test_no_dead_onclick_handlers` — прогонять
после каждой правки.

**Тесты.** Расширить существующий гейт: доля `empty()` с CTA не должна падать
(храповик, как `test_miniapp_bot_parity`): зафиксировать текущее число и
требовать роста, а не падения.

**Объём.** ~15 строк на первые 15 экранов + ~30 строк храповика.

## A-4 (P1). Три реализации spintax; массовые операции используют наивную

**Почему это проблема.** В проекте есть полноценный `services/spintax_engine/`
(18 файлов: лексер, парсер, валидатор, генератор, лимиты) и обёртка
`spintax_service.expand_template(..., seed=)`. Параллельно живут две наивные
копии на `re` + `random.choice`:
`dm_engine.expand_spintax` и `profile_setter_engine.expand_spintax`.

`op_worker` импортирует **наивную** версию из `dm_engine` минимум в трёх местах
(2254, 6163, 6252) — то есть массовая публикация и объявления в группах идут
через неё.

Свод классов багов (#7) требует «spintax-на-цель» именно как anti-detection
меру. Наивная реализация не умеет того, ради чего движок написан: валидации
(шаблон с одной альтернативой молча даёт одинаковый текст на всю рассылку),
детерминизма по seed, и главное — `generate_many(unique=True)`, то есть
гарантии, что 500 целей получат 500 **разных** текстов.

**Как пользователь сталкивается.** Пишет шаблон, рассылает по 500 каналам,
получает повторы — `random.choice` независим на каждой цели и по парадоксу
дней рождения даёт коллизии уже на десятках целей при небольшом числе
альтернатив. Модерация видит идентичные сообщения.

**Минимальное изменение.** Не удалять наивные функции (их зовут в других
местах), а перенаправить их на движок:

```python
def expand_spintax(text: str) -> str:
    """Сохранена как совместимый фасад; логика — в spintax_service."""
    from services import spintax_service
    return spintax_service.expand_template(text)
```

Отдельным шагом — в `mass_publish` и рассылке объявлений использовать
`expand_many(tpl, n, unique=True)` там, где число целей известно заранее.

**Переиспользуем.** `spintax_engine`, `spintax_service.expand_template` /
`expand_many` / `quality_warnings` (последняя уже умеет предупреждать о
бедных шаблонах — можно показывать в предпросмотре рассылки).

**Файлы.** `services/dm_engine.py`, `services/profile_setter_engine.py`
(фасады), `services/op_worker.py` (там, где известен размер выборки).

**Регрессии.** Движок строже наивной версии: шаблон, который `re` проглатывал,
может дать ошибку разбора. Поэтому фасад обязан быть fail-soft — при
исключении возвращать исходный текст, а не падать посреди рассылки.
Второе: `expand_template` без seed использует свой RNG — проверить, что
поведение «каждый раз разный вариант» сохраняется.

**Тесты.** `test_spintax_single_engine.py`: (1) `dm_engine.expand_spintax` и
`spintax_service.expand_template` дают одинаковое множество вариантов на
одном шаблоне; (2) битый шаблон не роняет фасад; (3) статический гейт — в
`services/` нет новых реализаций `{A|B}` через `re.sub` (свип, как
`test_no_duplicate_definitions`); (4) при `unique=True` на N целях нет
повторов, пока пространство вариантов это позволяет.

**Объём.** ~40 строк кода + ~70 строк тестов.

## A-5 (P2). 96 терминальных экранов бота без выхода

**Почему это проблема.** 96 мест в 37 хендлерах показывают финальный экран
(«❌ Ошибка…», «✅ Готово…») **без единой кнопки**. Пользователь упирается:
выйти можно только командой `/menu`, которую надо знать.

Показательно: 179 экранов вообще без `reply_markup`, из них 96 — терминальные
(не приглашения к вводу). Лидеры: `accounts.py` (17), `promo_platform.py` (12),
`network_bulk.py` (8), `quick_post.py` (8).

**Как пользователь сталкивается.** Импорт tdata: «❌ Ожидается ZIP-архив» —
и всё. Ни «Попробовать снова», ни «Назад к аккаунтам».

**Минимальное изменение.** Один общий хелпер вида `_terminal_kb(back_cb)` и
подстановка его в терминальные вызовы. Не переписывать хендлеры — только
добавить `reply_markup`.

**Переиспользуем.** `InlineKeyboardBuilder`, существующие `BmCb`-маршруты
разделов, паттерн `_back_cancel_kb` из `global_presence.py`.

**Файлы.** По убыванию плотности: `bot/handlers/accounts.py`,
`promo_platform.py`, `network_bulk.py`, `quick_post.py`, `admin.py`.

**Регрессии.** Низкие. Опасность одна: кнопка «Назад», ведущая в раздел,
которого у пользователя нет по тарифу — использовать существующие проверки
`require_plan`.

**Тесты.** Гейт-храповик `test_no_dead_end_screens.py`: посчитать текущее
число терминальных экранов без кнопок и запретить рост (снижать по мере
правок). Такой гейт защищает от регресса лучше, чем 96 точечных тестов.

**Объём.** ~10 строк хелпера + по 1 строке на экран + ~50 строк гейта.

**Минимальное изменение.** Для каждого — одно из двух: одна строка подключения

**Тесты.** Гейт `test_no_orphan_services.py`: список сервисов без единого

## A-7 (P3). Мёртвый дубль расчёта темпа

`session_simulator.get_adaptive_delay` (обучение на истории провалов) не
вызывается ниоткуда: реальный контур обучения — `pacing_engine`
(`record_result` → `get_multiplier` в `op_worker.get_adaptive_delay:220`).
`session_simulator.record_success/record_failure` вызываются по одному разу на
весь 9,5-тысячестрочный воркер, то есть их данные всё равно неполны.

Опасность — не в лишнем коде, а в том, что при следующей правке темпа легко
починить не тот механизм. Удалить неиспользуемую ветку либо явно пометить
её как исторический артефакт.

## Чего в этом аудите намеренно нет

* Новых модулей и подсистем — по условию задачи и по текущему приоритету
  «глубина, не ширина».
* Переписывания `mini_app/index.html` (монолит ~16 К строк): все предложения
  точечные, вынос экранов в `mini_app/screens/*.js` — отдельная работа,
  которую стоит делать попутно, а не как проект.
* Рефакторинга `op_worker.py` (9,5 К строк): он большой, но работает и покрыт
  гейтами; трогать его архитектуру без нужды дороже, чем терпеть размер.
