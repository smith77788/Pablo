# Автобэкап и восстановление БД

После инцидента 2026-08-30 (Postgres на Railway работал на эфемерном диске без
тома → пересоздание контейнера стёрло всю базу) система сама снимает бэкап и кладёт
его **вне Railway**.

## Два уровня защиты

1. **Постоянный том (Railway).** Обязательно: прикрепить Volume к сервису
   `postgres` с mount `/var/lib/postgresql/data`. Без тома данные эфемерны и
   исчезают при любом редеплое. Это первичная защита.
2. **Автобэкап вне контейнера (этот модуль).** `services/db_backup.py` регулярно
   снимает логический дамп (data-only, через `COPY`) и шлёт его документом в
   приватный Telegram-чат. Схема воспроизводится миграциями репозитория, поэтому
   дамп версионно-независим и не требует `pg_dump` в образе.

## Настройка

Переменные окружения:

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `DB_BACKUP_ENABLED` | вкл/выкл автобэкап | `1` (вкл) |
| `DB_BACKUP_CHAT_ID` | id приватного канала/чата назначения (бот должен быть его админом) | первый из `ADMIN_IDS` |
| `DB_BACKUP_INTERVAL_SEC` | период между бэкапами | `21600` (6 ч) |
| `DB_BACKUP_EXCLUDE` | таблицы через запятую, которые не бэкапить | список объёмных логов |

Рекомендуется завести **отдельный приватный канал** «Infragram backups», добавить
туда бота админом и указать его id в `DB_BACKUP_CHAT_ID` — тогда дампы не смешиваются
с личными сообщениями и переживают что угодно на стороне Railway.

## Ручной бэкап

Команда админа в боте: `/backup` — снимает дамп немедленно и шлёт в чат назначения.
Так удобно проверить, что всё настроено, не дожидаясь цикла.

## Формат архива

`tar.gz`:
- `manifest.json` — версия, время, список таблиц, счётчики строк, значения секвенций;
- `data/<table>.csv` — данные таблицы в формате CSV (COPY с заголовком).

Крупный архив режется на части `≤49 МБ` (лимит Telegram Bot API) с именами
`...tar.gz.partNNNofMMM`. Для восстановления части склеиваются по порядку.

## Восстановление

1. Собрать архив: если частей несколько — скачать все и склеить по порядку в один
   файл (`copy /b part001 + part002 ...` в Windows, `cat part* > backup.tar.gz` в *nix).
2. Поднять целевую БД со **схемой** (свежий старт приложения накатывает миграции —
   таблицы будут пустые, но правильной структуры).
3. Залить данные:

```python
import asyncio, asyncpg
from services import db_backup

async def main():
    archive = open("backup.tar.gz", "rb").read()
    pool = await asyncpg.create_pool("<DATABASE_URL целевой БД>")
    report = await db_backup.restore_archive(pool, archive)  # truncate=True по умолчанию
    print(report)  # {'restored': [...], 'skipped': [...], 'rows': N}
    await pool.close()

asyncio.run(main())
```

`restore_archive` работает при выключенных FK-триггерах
(`session_replication_role=replica`), чистит целевые таблицы одним `TRUNCATE ...
CASCADE` и заливает данные, затем выставляет секвенции. Таблицы из дампа, которых
нет в целевой схеме, пропускаются (перечислены в `report['skipped']`).

> Восстановление **перезаписывает** данные таблиц из дампа. Выполняйте на чистой
> или заведомо предназначенной для восстановления базе.
