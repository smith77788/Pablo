# План консолидации schema_v*.sql

Статус: план, ничего из него ещё не выполнено (кроме самого документирования).
Не пытаться реализовать всё за один проход — каждая фаза ниже самостоятельна,
проверяема и может быть сделана в отдельной будущей сессии.

Контекст: `.botmother/21_DATABASE_GOVERNANCE.md` прямо предостерегает от
"uncontrolled schema growth". Этот принцип в проекте уже нарушен — на
2026-07-09 в корне `tg-manager/` лежит **151 файл** `schema_v2.sql` …
`schema_v152.sql` (плюс базовый `schema.sql`), набранных за **~7 недель**
(первый коммит истории — 2026-05-22). Цель этого документа — не "починить"
это одним махом (это отдельная миграция БД с большим риском на проде,
который держит реальные аккаунты — см. `tg-manager/CLAUDE.md`), а дать
конкретный, дробимый на этапы, проверяемый путь выхода.

## 1. Факты, установленные аудитом (2026-07-09)

- Диапазон версий **сплошной**, пропусков нет: v2…v152 (151 файл), `schema_v1.sql`
  не существует — самая первая версия называется просто `schema.sql` (41
  строка, применяется первым, `_version_key`/`_version` дают ей 0).
- Суммарно ~4135 строк, 221 `CREATE TABLE`, 147 `ADD COLUMN`, 381 `CREATE INDEX`.
- **DROP-операторов нет вообще** — соответствует правилу из `docs/DATABASE.md`
  ("Только ADD COLUMN, не удалять"). Только один `ALTER COLUMN ... TYPE`
  (`schema_v20.sql`, `bot_routing_weights.weight` → `NUMERIC(10,2)`).
- Как это применяется — `database/db.py::create_pool()`:
  - на **каждом** старте процесса собирает `schema*.sql` из корня и
    `database/` (`glob.glob`), сортирует по числу в имени файла
    (`_version_key` = `int("".join(filter(str.isdigit, name)))`), дедуплицирует
    по basename и **выполняет все файлы заново**, statement-by-statement;
  - ошибка `already exists` / `duplicate key` молча проглатывается — то есть
    единственная причина, по которой это не ломается на пятой сотне повторных
    запусков, — идемпотентность каждого `IF NOT EXISTS`/`ADD COLUMN IF NOT
    EXISTS`;
  - есть таблица `schema_migrations` (filename, status, error_count,
    last_error, applied_at) — но она **только для наблюдаемости**, `create_pool()`
    не читает её, чтобы пропустить уже применённые файлы. Каждый деплой заново
    выполняет весь набор из 151+ файлов через connection pool.
- `tests/test_schema_lint.py` уже страхует три конкретных класса регрессий
  (все три реально ломали прод в прошлом, см. докстринг файла):
  1. `REFERENCES users(...)` вместо `platform_users`;
  2. volatile-функция (`NOW()`/`CURRENT_*`) в предикате `CREATE INDEX`;
  3. `CREATE INDEX` на таблицу в файле с номером МЕНЬШЕ, чем файл, создающий
     эту таблицу.
  Любая консолидация обязана продолжать проходить этот тест — он написан так,
  что работает по всему набору `schema*.sql` независимо от того, сколько их.
- **Найдено, но не багфикшу (см. `docs/AUDIT_LEDGER.md`)**: два имени таблиц
  создаются `CREATE TABLE IF NOT EXISTS` дважды в разных файлах —
  `platform_users` (`schema_v14.sql` и `schema_v39.sql`, вторая — no-op) и
  `strike_history` (`schema_v54.sql` и `schema_v134.sql`, вторая — no-op).
  Не баг (IF NOT EXISTS делает вторую версию безвредным no-op'ом), но это
  ровно тот класс дублирования, который стоит поймать лишним lint-тестом —
  см. §4, шаг для Phase, которая объединяет соответствующий диапазон.
- **Важное ограничение на способ консолидации**: часть файлов упомянута
  ПО ИМЕНИ в других местах кода — эти версии нельзя "сквошить" не обновив
  ссылку в том же коммите:
  - **User-facing** (сообщения администратору внутри бота, `bot/handlers/*.py`):
    `schema_v84.sql` (`activity_logger.py`), `schema_v99.sql`
    (`promo_platform.py`), `schema_v105.sql` (`ghost_hub.py`),
    `schema_v106.sql` (`content_mesh_hub.py`), `schema_v107.sql`
    (`clone_adapt_hub.py`), `schema_v108.sql` (`auto_funnel_hub.py`),
    `schema_v117.sql` (`persona_hub.py`), `schema_v118.sql` (`stars_hub.py`,
    дважды), `schema_v119.sql` (`audience_dna_hub.py`), `schema_v121.sql`
    (`narrative_hub.py`).
  - **Внутренние комментарии/докстринги** (не видны пользователю, но вводят в
    заблуждение при чтении кода, если файл исчезнет): `schema_v39.sql`
    (`tests/test_admin_users_columns.py`), `schema_v67.sql`
    (`tests/test_ecosystem_members_owner_column.py`), плюс несколько
    комментариев в `database/db.py`/`main.py`, ссылающихся на v124/v142/v143/
    v146/v147/v150 как объяснение defensive-фолбэков.
  - **Документация с диапазоном** (не проблема — тривиально обновляется):
    `database/README.md` и `docs/ARCHITECTURE.md` пишут "schema_v2.sql …
    schema_v150.sql" — уже устарело само по себе (реальный максимум v152),
    независимо от консолидации.

## 2. Почему нельзя просто взять и объединить все 151 файл

1. `create_pool()` не пропускает уже применённые файлы — он каждый раз
   реплеит весь набор. Значит корректность консолидации проверяется не
   "накатится ли новый файл", а **"даёт ли новый набор файлов ТОТ ЖЕ
   итоговый DDL, что и старая последовательность, что на чистой БД, что на
   БД, где старая последовательность уже накатана"**. Это две разные гарантии,
   и обе должны выполняться одновременно (прод — второй случай, свежий
   CI/staging — первый).
2. Хардкоженные ссылки на имена файлов (см. §1) означают, что не любой
   диапазон одинаково безопасно трогать — часть версий фактически "приколота"
   (pinned) кодом, который их упоминает.
3. Нет доступа к живому Postgres в песочнице этой сессии (см.
   `tg-manager/CLAUDE.md`, пункт про окружение) — значит самая сильная
   проверка (реальный `pg_dump --schema-only` diff до/после) доступна не в
   каждой сессии, и план должен предусматривать деградацию до статических
   проверок, когда живой БД нет, явно это помечая.
4. Проект активно растёт (v152 на 2026-07-09, до этого v150 неделю назад) —
   трогать самый свежий "хвост" истории того же типа риска, что редактировать
   ещё не устаканившийся код: велика вероятность конфликта с параллельной
   сессией, которая как раз добавляет новую миграцию.

## 3. Принцип консолидации

- **Объединять только литеральной конкатенацией**, не переписывать
  семантически. Один "squash"-файл = точное последовательное склеивание
  текста нескольких `schema_vN.sql` файлов в исходном порядке, с комментарием
  `-- originally schema_vN.sql` перед каждым исходным блоком. Никакого
  дедуплицирования/реордеринга операторов на этом шаге — это отдельный,
  более рискованный шаг, который делается only после того, как литеральная
  версия уже проверена и закоммичена (см. §5, «опционально»).
- **Никогда не трогать файл, упомянутый по имени где-либо в коде/тестах**
  (см. список pinned-версий в §1) — такие версии остаются самостоятельными
  файлами, разбивая диапазон на под-диапазоны. Это сильно проще, чем
  одновременно с squash обновлять сообщения бота (которые правит другой
  параллельный агент — см. ниже).
- **Не трогать "хвост"** — последние ~15-20 версий (сейчас это примерно
  v136+) не консолидировать: считать их "ещё не устоявшейся" историей.
- Имя нового squash-файла обязано сохранять корректную сортировку в
  `_version_key`/`_version` (`"".join(filter(str.isdigit, name))` — это ВСЕ
  цифры имени файла подряд, а не только "смысловое" число). Поэтому имя вида
  `schema_v0002_0013_baseline.sql` сортировалось бы как `20013` — то есть
  **после** v152, что сломает порядок. Правильная схема имени:
  `schema_v{B}_baseline.sql`, где `B` — верхняя граница склеенного диапазона
  (например `schema_v13_baseline.sql` для диапазона v2–v13). Это даёт то же
  положение в сортировке, что раньше занимал `schema_v13.sql`, а поскольку
  склеенный файл уже содержит всё от A до B по порядку, итоговый эффект
  идентичен применению A..B по очереди.

## 4. Фазы (каждая — отдельный, самостоятельно проверяемый коммит)

комментариев): v124, v142, v143, v146, v147, v150.

| 2 | v14–v38 | 25 | v14 — первое создание `platform_users`. Не включает pinned v39. |

Итого фазами 1–8 покрывается 121 из 151 файлов (151 − 30 pinned/хвост), при

остаются как есть — переоценить в будущей сессии, когда они перестанут быть
"свежим хвостом" и/или когда сообщения бота, ссылающиеся на них, будут
осознанно переписаны (см. §6).

### Рецепт одной фазы (одинаковый для всех, на примере Фазы 1: v2–v13)

1. **Заморозить диапазон.** Для каждого N в диапазоне
   `grep -rn "schema_v{N}\.sql" --include="*.py" --include="*.md" --include="*.html" .`
   — должно быть пусто (кроме общих упоминаний диапазона в
   `database/README.md`/`docs/ARCHITECTURE.md`, которые в любом случае
   обновляются отдельным шагом). Если хоть один файл диапазона неожиданно
   зацеплен где-то в коде — исключить его из диапазона (сузить фазу).
2. **Склеить литерально**: новый файл `schema_v13_baseline.sql` = содержимое
   `schema_v2.sql` … `schema_v13.sql` строго по порядку версий, перед каждым
   куском — комментарий `-- originally schema_vN.sql`.
3. **Проверка отсутствия мутации контента** (без живого Postgres, чисто
   текстовая): взять склеенный файл, вырезать из него все добавленные
   `-- originally schema_vN.sql` комментарии — результат обязан быть
   побайтово равен конкатенации исходных файлов в том же порядке. Это гарантия
   "ничего не потеряно и не переписано" на уровне текста, до всякого SQL.
4. `git rm schema_v2.sql schema_v3.sql ... schema_v13.sql` (per-file, не
   `git rm -A`, чтобы не задеть ничего лишнего).
5. **Обновить общие упоминания диапазона**: `database/README.md`,
   `docs/ARCHITECTURE.md`, `docs/DATABASE.md` — если там фигурирует список/
   количество файлов, поправить на актуальное.
6. **Прогнать `tests/test_schema_lint.py`** — обязан пройти на новом наборе
   файлов (он читает `schema*.sql` из файловой системы каждый раз заново,
   так что автоматически подхватит и новый squash-файл, и отсутствие
   удалённых).
7. **(Когда доступен Postgres — не в этой песочнице, но обязательно перед
   реальным деплоем фазы в будущей сессии)**: поднять одноразовый Postgres
   (`docker run --rm -e POSTGRES_PASSWORD=x -p 5432:5432 postgres:16` или
   аналог), применить СТАРЫЙ набор файлов в БД №1, применить НОВЫЙ набор
   (после squash) в БД №2, сравнить `pg_dump --schema-only` для обеих — diff
   обязан быть пуст (не считая служебной таблицы `schema_migrations`, у неё
   будут разные списки `filename`, это ожидаемо и не является расхождением
   схемы данных). Это единственная проверка, которая по-настоящему
   подтверждает поведенческий паритет на СВЕЖЕЙ базе (CI/staging) — статические
   шаги 1–6 её не заменяют, только снижают риск до этого момента.
8. Коммит отдельно от всего остального:
   `chore(schema): squash v2–v13 → schema_v13_baseline.sql (12 файлов → 1, без изменения поведения)`.
9. После деплоя в прод — проверить логи `create_pool()`
   (`Schema migration: N files OK, 0 with errors`) и таблицу
   `schema_migrations`: новый файл должен появиться там со `status='ok'`,
   `error_count=0` (на прод-БД все операторы внутри — уже применённые
   `IF NOT EXISTS`/`ADD COLUMN IF NOT EXISTS`, так что весь squash-файл должен
   отработать как чистый no-op).

Каждая следующая фаза (2–8) — тот же рецепт с другим диапазоном. Не
обязательно делать их подряд в одной сессии — каждая абсолютно независима от
соседних (диапазоны не пересекаются, pinned-версии между ними не трогаются).

## 5. Опционально, ПОСЛЕ того как фазы 1–8 закоммичены и провалидированы

Дедупликация двух известных дублей (`platform_users`: v14 vs v39,
`strike_history`: v54 vs v134) — сейчас v14 и v54 попадут в разные
squash-файлы (Фаза 2 и Фаза 3), а v39/v134 — pinned, остаются отдельными
файлами. Реальное устранение дубля (не просто терпимость к нему через
`IF NOT EXISTS`) означает редактирование pinned-файла v39/v134, чтобы убрать
из него уже-существующий `CREATE TABLE` — это требует:
- построчного сравнения обеих версий DDL таблицы (столбцы/типы/constraints),
  чтобы доказать, что убираемая версия строго не добавляет ничего нового
  относительно первой (иначе итоговая схема на новой БД потеряет колонку);
- отдельного, самого по себе rev-review коммита, НЕ смешанного со squash;
- в этот же момент можно добавить в `tests/test_schema_lint.py` lint-проверку
  "одна таблица не создаётся `CREATE TABLE` дважды в разном имени файла" —
  сейчас её нет, добавлять её ДО того, как дубли устранены, приведёт к
  красному тесту на существующем состоянии репозитория.

## 6. Что НЕ входит в этот план (сознательно)

- Переписывание захардкоженных сообщений бота вида "Обратитесь к
  администратору для применения миграции `schema_v117.sql`" на
  version-agnostic формулировку (например, "требуется применить последние
  миграции БД") — это изменение user-facing текста в `bot/handlers/*.py`,
  то есть бизнес-логика/UX за пределами этой задачи (правится другими
  параллельными агентами по мере работы над конкретными хабами). Отмечается
  здесь как **предпосылка** для того, чтобы когда-нибудь снять pin с
  v84/v99/v105–v121: пока сообщения жёстко ссылаются на конкретное имя
  файла, тот файл нельзя переименовать/склеить без синхронного изменения
  этого сообщения — то есть эти версии переходят из "не трогать в фазах
  1–8" в "можно консолидировать" только вместе с отдельной задачей на
  ревью этих ~10 сообщений.
- Вариант "Б" — заменить всю историю на один `pg_dump --schema-only` от прод-БД
  как новый `schema.sql` и архивировать старые файлы. Концептуально проще, но:
  требует доступа к прод-БД для снятия дампа, разом делает все ~10
  захардкоженных сообщений мёртвым кодом (что не ломает функциональность —
  таблицы уже есть, но сообщение никогда не покажется и станет вводящим в
  заблуждение), и не оставляет постепенного пути отката по фазам. Рассмотреть
  только после того, как поэтапный вариант (§4) уже наведёт порядок в старой
  части истории и станет ясно, оправдан ли более резкий шаг.
- Оптимизация `create_pool()`, чтобы пропускать уже применённые файлы через
  таблицу `schema_migrations` вместо реплея всех файлов на каждом старте —
  реальная идея для сокращения времени старта, но отдельная задача с
  собственным риском (нужна гарантия, что таблица `schema_migrations`
  никогда не разъедется с реальным состоянием БД, например из-за ручных
  правок на проде). Не часть консолидации файлов, не делать заодно.

## 7. Как читать прогресс

Каждая выполненная фаза добавляет запись в `docs/AUDIT_LEDGER.md`
(`## tg-manager: schema squash — Фаза N (vA–vB) — <дата>`) с тем, что именно
объединено, каким тестом проверено, и (если был доступен Postgres) с итогом
`pg_dump` diff. Перед тем как начинать любую фазу в новой сессии — сначала
смотреть туда, не сделана ли она уже.
