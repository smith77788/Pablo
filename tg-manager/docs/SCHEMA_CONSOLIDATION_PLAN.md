# Свёртка истории миграций

На него ссылаются `docs/DATABASE.md`, `docs/ARCHITECTURE.md` и
`database/README.md`. До 2026-09-03 файла не существовало — ссылки вели в пустоту,
и это же породило устойчивое заблуждение, что история миграций проигрывается
целиком при каждом старте. Она не проигрывается: журнал `schema_migrations`
пропускает применённые файлы с 2026-07. Ниже — что осталось сделать.

## Что уже решено

| Проблема | Состояние |
|---|---|
| Повторное проигрывание всей истории на каждом старте | **Закрыто** журналом `schema_migrations` (skip по статусу `ok`) |
| Файл рвётся посередине и оставляет схему в полусостоянии | **Закрыто**: транзакция на файл, savepoint на оператор |
| `ALTER`, ждущий блокировку, вешает старт | **Закрыто**: `lock_timeout` + повтор, приложение стартует в любом случае |
| Молчаливый старт на битой схеме | **Закрыто**: проверка критичных таблиц, `SCHEMA_STRICT=1` для отказа старта |
| Чистая база прокатывает 194 файла подряд | **Механизм готов**, снимок не снят — фаза 1 ниже |
| 194 файла в репозитории | Открыто — фазы 2–3 |

## Чего это стоит сейчас

Ежедневная работа от числа файлов почти не страдает: обновление их пропускает.
Платят двое:

* **новое окружение** — первый старт прокатывает всю историю подряд, и чем она
  длиннее, тем выше шанс, что развалится давняя миграция, чей контекст уже никто
  не помнит;
* **человек** — 194 файла в корне, и чтобы узнать структуру таблицы, надо
  прочитать всю историю её изменений.

## Фаза 1 — снять baseline (готово к исполнению)

Механизм в рантайме уже есть: если рядом лежат `schema_baseline.sql` и
`schema_baseline.manifest`, а база **заведомо чистая** (журнал пуст И нет
`tg_accounts`), применяется снимок, а файлы из манифеста помечаются
применёнными. У существующего окружения baseline не берётся никогда — ни при
каком стечении обстоятельств снимок не ляжет поверх живых данных.

```bash
# 1. поднять пустую базу текущим кодом — она прокатит всю историю
createdb infragram_baseline
DATABASE_URL=postgres://…/infragram_baseline python main.py   # дождаться "Schema migration: … 0 with errors"

# 2. снять снимок с неё
python deploy/scripts/make_schema_baseline.py \
    --database-url postgres://…/infragram_baseline

# 3. проверить, что ЕЩЁ ОДНА чистая база встаёт снимком
createdb infragram_check
DATABASE_URL=postgres://…/infragram_check python main.py      # ждём "Schema baseline применён"
```

Проверка приёмки: во второй базе `SELECT count(*) FROM schema_migrations` равен
числу строк манифеста + 1, а структура совпадает с первой базой
(`pg_dump --schema-only` обеих, `diff`).

Снимок снимают с базы, прошедшей историю целиком, а не с продовой: в проде за
годы осели ручные правки, расширения и индексы, которых нет в истории, и они
молча попали бы в baseline как норма.

## Фаза 2 — убрать покрытые файлы из репозитория

Только после того, как фаза 1 отработала хотя бы на одном реальном новом
окружении. Файлы из манифеста переезжают в `schema/history/` — не удаляются:
они остаются единственным описанием того, почему схема такая, какая есть.
Рантайм их не читает (`glob` смотрит корень и `database/`), журнал уже помечен.

Откат: вернуть файлы в корень и удалить `schema_baseline.*` — механизм
выключается их отсутствием, отдельного флага не нужно.

## Фаза 3 — правило на будущее

Новая миграция — по-прежнему новый `schema_vN.sql`. Порог свёртки: следующий
baseline снимается, когда после предыдущего накопилось **больше 40** файлов.
Так история не растёт бесконечно, а свёртка остаётся дешёвой и предсказуемой
процедурой, а не разовым героизмом.

## Чего этот план сознательно не делает

Не переводит проект на Alembic. Свой раннер уже умеет ровно то, ради чего к
Alembic идут (журнал, транзакция на файл, таймаут блокировки, статус в базе), а
перевод 194 файла в ревизии Alembic — это отдельная миграция самой миграционной
системы, с собственным риском и без выигрыша поверх baseline.
