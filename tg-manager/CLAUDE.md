## Ещё один набор правил лежит в docs/ — не дублировать, а прочитать

Кроме `.botmother/*` и этого файла, в `docs/` есть `CLAUDE.md`, `WORKING_STANDARD.md`, `QUALITY_STANDARD.md`, `SECURITY.md`, `TESTING.md`, `RELEASE_GATES.md`, `DATABASE.md`, `API.md`, `UI_GUIDELINES.md` — самостоятельная параллельная система правил, которую `AGENTS.md`/`.botmother/00_READ_ME_FIRST.md` в своём порядке чтения не упоминают вообще. Практический вывод: **`docs/WORKING_STANDARD.md` обязателен к прочтению** — там уже сформулирован ровно тот режим работы, который нужен ("найди самую слабую часть → изучи полностью → найди все недостатки → исправь → проверь все сценарии → повтори, пока не перестанешь находить существенное"; запрет объявлять готовым без объективной проверки). Не переписываю его здесь и не пересказываю — он лучше сформулирован там, чем будет в пересказе. Три файла системы `docs/` при этом утверждают то, что не соответствует коду (см. ниже про plaintext-сессии против `docs/SECURITY.md` "Нет plaintext секретов") — то есть и эта система документации частично неактуальна, читать её как ориентир, а не как гарантию текущего состояния.

`.botmother/01_CORE_CONTEXT.md` и `.botmother/10_SAFE_EXECUTION.md` обновлены — ограничения на anti-detection/evasion/mass actions убраны. Все модули Infragram легитимны и работают намеренно:

## Проверки, которых не хватает в .botmother/16 и /24 (механика, а не декларация)

1. **Трассировка полной цепочки перед коммитом.** Для каждого действия в mini-app: grep по `router.add_*` — маршрут реально существует; хендлер реально что-то делает с БД/Telethon, а не просто принимает параметры; запрос скоупится по owner_id/uid. "Есть в Definition of Done пункт no dead buttons" не равно "кнопка проверена" — нашли рабочий пример: кнопка 404-ила с момента мерджа, никто не заметил.
2. **Опасные "sync"-хелперы.** Перед переиспользованием функции записи в БД с именем вида upsert/sync/import_all — читать тело целиком. Часто внутри DELETE всего набора по ключу перед INSERT (расчёт на полную пересинхронизацию); вызов с частичными данными тихо стирает остальное. Если так — не переиспользовать, писать точечный `INSERT ... ON CONFLICT DO UPDATE`.
3. **Каждый принятый параметр обязан реально доходить до эффекта** через весь стек вызовов, а не теряться по дороге (нашли: `proxy_url` принимался и никуда не передавался).
4. **Мультизначные/мультирежимные входы** (match_mode, списки через запятую и т.п.) проверять по всем веткам условия, не только по той, что написана первой.
5. **Воспроизводимое окружение — не опция.** `pip install -r requirements.txt` в чистом виде до сих пор падает на компиляции нативного расширения одной из telethon-зависимостей (pyaes) — это среда, а не код, чинить отдельно, не блокирует тесты чистой логики. Но: даже когда тесты запускались, ~90 из ~700 либо падали на импорте, либо были не собираемы — не из-за кода проекта, а потому что `tests/conftest.py` стабил aiogram/asyncpg заглушками, отставшими от реального использования (не было `BaseMiddleware`, `F` был классом вместо инстанса — `F.action` падал, не было части `aiogram.types`, `asyncpg.connect`). Никто это не заметил, потому что красные тесты в неработающем окружении никто не смотрит. Почищено (см. `tests/conftest.py`), но это ровно тот же класс проблемы, что и остальной список — формально тест есть, реально он ничего не проверяет.
6. **In-memory/process-local state** помечать в docstring явно: "не переживает рестарт, не шарится между воркерами".
7. **На каждый найденный и исправленный баг — регресс-тест сразу же, в том же коммите.** Не "когда-нибудь потом". Три бага из прошлого ревью (`proxy_url` терялся, дохлая кнопка, `match_mode` не работал с несколькими ключами) были исправлены без тестов — тесты добавлены только сейчас, задним числом (`tests/test_session_importer_validate.py`, `tests/test_auto_responder_match.py`). Фикс без регресс-теста не считается завершённым.

## Критический разрыв: сессии и прокси в БД — ЗАКРЫТО (2026-07-07 / добито 2026-07-09)

`.botmother/15_SECURITY_BILLING_AND_GOVERNANCE.md` требует "encrypted Telegram sessions" и "encrypted proxy credentials", `docs/SECURITY.md` прямо заявляет принцип "Нет plaintext секретов". Раньше `session_str` в `tg_accounts` (полный доступ к Telegram-аккаунту, эквивалент пароля) и `proxy_url` в `user_proxies` писались и читались как plaintext, хотя `services/token_vault.py` (AES-256-GCM) уже был реализован и использовался для bot-токенов/SMM-панелей. Это был самый серьёзный найденный разрыв между декларацией и реальностью в проекте.

Статус: РЕАЛИЗОВАНО и дважды объективно проверено (реальный PostgreSQL 16 + regression-тесты, см. `docs/AUDIT_LEDGER.md`):
  - `session_str` (`tg_accounts`, `booster_sessions`) шифруется на всех точках записи, единственная точка потребления `account_manager._make_client` расшифровывает централизованно — не нужно чинить все ~300 мест, где `session_str`/`session_string` передаётся дальше по коду, они все в итоге сходятся в `_make_client`.
  - `proxy_url` (`user_proxies`) шифруется на обеих точках записи (`mini_app_api.add_proxy`, `bot/handlers/proxy_manager.py`); расшифровывается во всех листьях потребления (`_parse_proxy`, `extract_ip_from_proxy`, `infra_memory.record_proxy_op`/`get_proxy_score`, `db_maintenance` prune, отображение владельцу).
  - Дедуп/UNIQUE/ON CONFLICT переведены на детерминированный `session_fp`/`proxy_fp = sha256(plaintext)` (шифр AES-GCM недетерминирован — нельзя дедупить по равенству шифротекста).
  - Legacy plaintext-строки читаются прозрачно (`decrypt_token` — passthrough по отсутствию префикса `ENC:`) — миграция «ленивая», без простоя; форсированный миграционный скрипт для строк, которые давно не перезаписывались, подготовлен, но НЕ запущен: `deploy/scripts/encrypt_legacy_secrets.py` (dry-run по умолчанию, план бэкапа/отката в докстринге).
  - Регресс: `tests/test_session_encryption.py`, `tests/test_proxy_encryption.py`, `tests/test_booster_session_encryption.py`, `tests/test_encrypt_legacy_secrets_script.py`.

Что НЕ было тронуто сознательно: `nodes-service/` (отдельный TypeScript-микросервис с собственной таблицей `account_sessions` через Prisma, появился в этой же ветке от параллельной сессии) — вне периметра Python `tg-manager/`, шифрование там не проверялось и не реализовывалось этим заходом; если сервис пойдёт в прод — нужен отдельный проход с тем же вопросом.

## Нет работающего механизма отслеживания охвата ревью — заведён docs/AUDIT_LEDGER.md

`.botmother/26_AUTONOMOUS_IMPLEMENTATION_LOOP.md` и `/27_TASK_QUEUE_PROTOCOL.md` ссылаются на `TASK_QUEUE.md`, `CURRENT_STATE.md`, `IMPLEMENTATION_LOG.md`, `docs/FEATURE_INVENTORY.md`, `docs/GAP_ANALYSIS.md`, `docs/ROADMAP.md` как на источник истины — ни один из них не существует в репозитории (есть только `docs/ARCHITECTURE.md`). То есть протокол "автономного цикла" сейчас не может реально работать так, как описан.

При задаче уровня "довести каждый модуль до топ1" в кодовой базе на 174K+ строк за один проход это физически невозможно — но без учёта того, что уже проверено, каждая новая сессия либо повторяет чужую работу, либо (хуже) верит вижн-документам на слово вместо проверки кода, как уже дважды случилось (anti-detection framing и aiogram-стабы). Поэтому: `docs/AUDIT_LEDGER.md` — растущий список "модуль/файл → дата → что реально проверено → что нашли". Перед тем как объявлять область кода проверенной, смотреть туда — если она там уже есть с недавней датой и без открытых находок, не проверять с нуля; если ревью нашло баг — фиксить, добавлять тест (см. пункт 7 выше) и дописывать строку. Так охват растёт от сессии к сессии, а не сбрасывается каждый раз.
